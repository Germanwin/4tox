# Публичные комнаты EOS — подготовка и границы проверки

Статус: координатор и ограниченная клиентская конфигурация EOS установлены на
VPS. На одном Mac проверено создание и закрытие реальной EOS-комнаты через
публичный координатор. До публичного запуска нужны подпись и приёмка на
нескольких устройствах и сетях.

## Компоненты

Координатор хранит коды, полномочия, состояние выбора хозяина и последнюю
зашифрованную копию. Он не рассчитывает мир и не пересылает игровые кадры.
Клиент-хозяин запускает собственный Node; его worker считает мир. Между
клиентами трафик игры идёт через EOS P2P и туннель. Адрес EOS получает только
участник после входа в координатор; туннель проверяет HMAC ответа на случайный
вызов с ключом, производным от полномочия. Само полномочие по P2P не передаётся.
Полномочие — доказательство членства в нашей комнате;
строка Product User ID не рассматривается как доказательство личности.

Служба `game/server/coordinator.js` слушает только loopback. Доступ снаружи —
HTTPS Caddy → существующий `4tox.service` → опциональный маршрут
`/api/eos-coordinator/*` → loopback координатора. Это только управляющий
канал. По умолчанию маршрут выключен; он включается переменной
`COORDINATOR_PROXY_PORT`. Координатору разрешается использовать последний
проверенный адрес из X-Forwarded-For только с доверенного loopback-прокси
(`COORDINATOR_TRUST_LOOPBACK_PROXY=1`). До выкладки нужно проверить реальную
конфигурацию Caddy: она должна стирать внешние поддельные X-Forwarded-For.
Caddy по умолчанию игнорирует входящие X-Forwarded-* от недоверенных клиентов:
https://caddyserver.com/docs/caddyfile/directives/reverse_proxy

Код: 10 символов из 32-символьного алфавита (50 бит), генерируется
криптографически. Выдаваемое каждому участнику полномочие — 32 случайных
байта; хранятся хеши. Лимит — 600 запросов, 20 попыток входа и 8 созданий
в минуту на адрес, а также 120 запросов в минуту на полномочие участника,
1000 записей и 32 МиБ суммарных копий; запрос не более 8 МиБ. Это начальные
ограничения, не доказательство устойчивости к распределённому перебору.

Хозяин получает аренду на 10 секунд, heartbeat каждые 2 секунды. Время аренды
отсчитывается клиентом консервативно с начала HTTP-запроса. Локальный Node
отдельно прекращает обработку и закрывает worker, если продление прекратилось,
в том числе при зависании Godot. При истечении аренды клиент останавливает
сервер и туннель; гости приостанавливают приём кадров и
команды. Координатор увеличивает поколение и назначает живого кандидата на
15 секунд. При отказе или тайм-ауте выбирается следующий. Кандидат получает
копию, проверяет её контрольную сумму, восстанавливает отдельный каталог,
запускает Node и EOS, после чего подтверждает назначение. Остальные
переподключаются по тому же коду. При отсутствии копии, отказах или
недоступности координатора восстановление ограничено 45 секундами и сообщает
об ошибке. Старый хозяин не получает управление обратно автоматически.
Это не защита от намеренно изменённого клиента, отключающего проверки.

Копии создаются ориентировочно каждые 3 секунды, сжимаются gzip и передаются
по HTTPS. При отсутствии успешного сохранения 15 секунд хозяин отказывается
от аренды. При внезапном падении теряются действия после последней принятой
координатором копии: срок зависит от задержки создания/передачи, а не только
от интервала. Подтверждение команды локальным Node не означает подтверждение
копии на VPS. Резервные данные содержат токены локальной комнаты и хранятся
шифрованными AES-256-GCM; данные удаляются при удалении записи. Файл с
локальными полномочиями для возврата хранится в приватном каталоге приложения
(на macOS права 0700/0600); Keychain для него не используется. EOS SDK может
независимо использовать системное хранилище.

Если никто не подключён, локальная Node-комната и её данные удаляются по
существующему правилу 30 секунд. Координатор выявляет отсутствие heartbeat
через 15 секунд и удаляет запись через 30 секунд после последнего heartbeat.
Живой
одинокий хозяин может ждать гостя до 5 минут: это не изменение правила о
полностью неактивной комнате. Запуск лобби требует двух присутствующих и
готовых игроков. Игроки, сохранившие полномочие, могут возвращаться в комнату;
начатая партия не принимает нового участника вместо выбывшего.

## EOS и сборки

В Epic Developer Portal используется клиент для публичной настольной игры с
минимальной политикой для EOS Connect Device ID и P2P. Не использовать политику
доверенного сервера и не выдавать доступ к прочим сервисам без необходимости.
EOS Lobbies не используются.
Для каждого физического устройства Device ID должен давать собственный PUID;
несколько окон одного устройства не являются подтверждёнными независимыми
EOS-игроками.

Проверка 2026-11-07: в портале для существующего `4tox-client` сохранена
политика `Custom` с `User required`, без дополнительных разрешений служб;
реальный SDK с её параметрами выполнил вход Device ID и создал P2P-хост на
macOS. Затем параметры установлены на VPS: Godot получил их по публичному
HTTPS, вошёл в EOS, создал комнату через игровой код, отправил резервную копию
и вышел. Подключение второго физического устройства и relay не проверялись;
этот успех не является проверкой интернет-матча.

`COORDINATOR_CLIENT_CONFIG` указывает на отдельный файл JSON с полями
`product_name`, `product_version`, `product_id`, `sandbox_id`, `deployment_id`,
`client_id`, `client_secret`. Это **публичная клиентская** конфигурация,
сервис отдаёт только перечисленные поля без авторизации. Её можно извлечь из
ответа или памяти клиента; там не должно быть серверных полномочий. Секрет
шифрования состояния координатора — отдельный файл, клиент его не получает.
Настоящие значения не входят в репозиторий или текущие артефакты сборки.
Настройка читается клиентом через HTTPS автоматически; разработческий
`user://eos.cfg` остаётся только для прямых тестов без координатора.

Developer ID на этой машине отсутствует. Аддон в старом исследовании
наблюдался вместе с записью macOS Keychain, но происхождение и содержимое
записи по одному названию не доказаны. Нельзя обещать отсутствие Keychain или
системного диалога. Для релиза требуется подписать вложенные компоненты и
проверить designated requirement, затем на чистом профиле испытать первый и
повторный запуск, несколько комнат, обновление и запуск из `/Applications`.
Отдельно проверить запуск из dmg и Windows. Не менять защиту системы и не
запрашивать пароль связки ключей.

Доступная статическая проверка установленного macOS SDK: в бинарнике указана
версия `1.19.1.2-53289219`; динамическая
библиотека связана с Security.framework и импортирует `SecItemAdd`,
`SecItemCopyMatching`, `SecItemDelete`; в её строках есть имена записей auth и
connect. Это подтверждает наличие кода для системного хранилища, но не
определяет, какой вызов в текущем сценарии пишет запись или вызывает диалог.
Windows DLL импортирует `CredReadW` и `CredWriteW`; реальное поведение входа
на Windows не проверено. Выводы о содержимом токена и отсутствии диалогов по
статическому анализу не делаются.

При повторной проверке собранного macOS-приложения наблюдалась длительная
блокировка главного потока внутри вызова EOS `EOS_Connect_CreateDeviceId` →
`SecItemCopyMatching` → Security.framework. Это реальное наблюдение по стеку
процесса, но оно не определяет содержимое записи и не доказывает причину или
наличие видимого диалога. На машине нет действующей подписи Developer ID;
проверка подписанного обновления и устранение задержки остаются открытыми.
Пароль Keychain не запрашивался, настройки системы не менялись.

Настоящий SDK на имеющемся профиле macOS вошёл при двух последовательных
запусках отдельного процесса с одной и той же анонимной идентичностью;
сравнивались только одноразовые проверочные значения без вывода PUID. Этот
headless-прогон не заменяет чистый профиль, подписанное обновление или
наблюдение за системными диалогами.

В более новом EOS SDK 1.19.2.1 Epic описывает исправление пропущенного события
закрытия P2P после внезапного обрыва сети. Установлен 1.19.1.2; обновление
аддона и совместимость бинарников ещё не проверены. Поэтому обнаружение
сетевого обрыва на текущей версии требует испытания на реальных устройствах:
https://dev.epicgames.com/docs/epic-online-services/release-notes

Прямой P2P может раскрывать участникам сетевые адреса; relay может менять
наблюдаемый маршрут, но факт и видимость адресов в этой версии EOS не
проверены. Нельзя обещать анонимность от провайдеров, Epic или координатора.
Влияние relay на RTT без двух реальных сетей не измерено; принудительный relay
не включён.

## Выкладка и откат

2026-11-07 по разрешению заказчика установлен отдельный
`4tox-coordinator.service`, а в действующий `server.js` добавлен только
проверенный маршрут `/api/eos-coordinator/*`. Игра и координатор слушают только
loopback; существующий HTTPS-маршрут Caddy не менялся и Caddy не перезапускался.
Резервная копия: `/root/4tox-eos-deploy-sLkFzN0Q/4tox-before.tgz`, оригинал
серверного файла и прежняя конфигурация службы — в том же каталоге. Исходный
`COMMIT` оставлен прежним: выложено точечное изменение, а не git-коммит.
Godot прошёл через публичный HTTPS создание и вход в комнату, выбор и активацию
нового хозяина и выход. Позже `/config` настроен клиентскими параметрами EOS.
Тест не проверяет настоящий EOS P2P. При первом запуске преждевременная
проверка порта вызвала автоматический откат; повтор с ожиданием готовности
завершился успешно.

Файл `/etc/4tox/eos-client.json` должен быть читаем службой `4tox` (например,
root:4tox, 0640); после создания потребуется перезапуск только
`4tox-coordinator.service`. После восстановления связи файл был установлен,
служба координатора перезапущена отдельно и публичный HTTPS проверен. Значения
клиентской политики доступны клиентам и
не являются серверным секретом. Ключ шифрования `/etc/4tox/coordinator.key`
отдельный, не передаётся игрокам и не должен попадать в чат или конфигурацию
EOS. Созданный на VPS ключ сохранять при перезапуске координатора.

Шаблоны: `game/server/deploy/4tox-coordinator.service` и
`game/server/deploy/game-coordinator.conf`. До выкладки проверить на staging:
версию Node и systemd, возможность `LoadCredential`, пользователя `4tox`,
отдельный `/var/lib/4tox-coordinator` с правами 0700, конфигурацию клиента и
ключа у root. Ключ шифрования передаётся службе через systemd credential,
не через клиентский конфиг и не в URL. Состояние является временным и не
совместимо с произвольным откатом или заменой ключа: ротацию выполнять при
пустом реестре либо через отдельную проверенную миграцию. Потеря ключа
означает потерю зашифрованных резервных копий.

Сначала проверить `docs/DEPLOY.md`, наличие активных партий и сухой rsync,
сохранить резервные копии кода, конфигурации 4tox.service и нового каталога
состояния, установить шаблоны и отдельно проверить loopback health и HTTPS
контрольный путь. Затем только по разрешению перезапустить координатор и
`4tox.service`, проверить обе службы и существующий VPN. **Caddy не
перезапускать**; новый маршрут использует уже существующий `/api/*`. Откат —
отключить drop-in и службу координатора, вернуть сохранённый код и настройки,
перезапустить только `4tox.service`, восстановить соответствующую версию
состояния и проверить `/api/build`, игру и работоспособность VPN. Не совмещать
старый код с состоянием новой схемы без проверки. Никаких действий на VPS без
отдельного разрешения.

## Что измерено и что остаётся

Исправление входа с одинаковыми именами: клиент при занятом имени предлагает
свободный вариант с номером и сообщает отдельные причины отказа. Локально
прошли семь интеграционных сценариев миграции с одинаковым исходным именем;
также три участника вошли через реальный HTTPS-координатор на VPS с локальным
тестовым транспортом. Реальное EOS-соединение между компьютерами в этом
прогоне не проверялось. Два EOS-окна одного профиля macOS используют один
Device ID; самоподключение теперь сообщает об этом отдельно.

Локальный переносимый checkpoint карты 64: 634 134 байта исходного JSON,
116 612 байт gzip; base64 даёт около 155,5 КБ на отправку. При интервале
3 с это примерно 52 КБ/с на комнату без учёта HTTPS и изменения мира.
Это замер одного небольшого мира, не верхняя граница. Браузерная приёмка с
306 жителями: WebSocket 10 кадров/с, последний кадр 15 806 байт, максимальный
интервал 119 мс; это не EOS и не интернет-замер.

Локальный синтетический прогон хранилища с 20 независимыми комнатами,
80 записями участников и разными копиями по 116 612 байт: 1,395 с на
создание и запись всех комнат, p95 записи копии 28 мс, CPU пользователя
113 мс и системы 135 мс за прогон, RSS 73 МиБ в момент завершения. Метаданные
заняли 20 353 байта, сами копии хранятся в отдельных шифрованных файлах.
Это однократный тест диска Mac без HTTP, EOS, задержек сети и длительной
нагрузки; RSS — значение в конце, не зафиксированный пик. Он не определяет
пропускную способность VPS или частоту успешных интернет-подключений.

Автоматические локальные прогоны используют настоящие Godot и Node, но
заменяют EOS на TCP-петлю и координатор на loopback HTTP. Не проверены:
пара устройств в разных сетях, четыре устройства, две группы через интернет,
публичная клиентская политика и сборка, macOS Keychain на чистом профиле,
Windows, relay и его задержка, подтверждение связи P2P с выбранным маршрутом,
устойчивость к длительному сну/смене сети, нагрузка координатора при множестве
комнат, а также аудит безопасности/нагрузки перед публикацией. Эксплуатационная
готовность не подтверждена; данные о задержке и возможном откате на реальных
сетях отсутствуют.

Проверочная сборка 2026-11-07: экспорт macOS и Windows, проверка встроенного
Node через `/api/health`, запуск macOS-приложения до получения кадра, проверка
содержимого смонтированного DMG и целостности Windows ZIP прошли. Подпись macOS
только локальная ad hoc; Windows не запускалась. В пакет не вкладывалась
настоящая клиентская конфигурация EOS: она автоматически получается от
настроенного HTTPS-координатора. Сетевые игровые файлы в свежих пакетах macOS
и Windows совпадают с проектом и между собой. Это проверочные артефакты, не
релиз.

В локальном тесте потери хоста с двумя участниками восстановление заняло
10,7 с; прогон с тремя участниками показал 16,3 с, с четырьмя — 16,6 с.
Последние два измерения включают дополнительные три секунды наблюдения
кадров после миграции. Это единичные измерения на одной машине и не оценка
интернет-соединения, EOS или relay.
