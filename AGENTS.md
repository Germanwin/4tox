# 4tox — правила работы агента

## Мультиплеер с 2026-10-27: мир считает сервер

Создатель лобби больше **не** авторитет: его браузер — обычный клиент. Мир
живёт в `worker_threads.Worker` комнаты (`game/server/room-worker.js`),
`game/server/room-runtime.js` ведёт очередь/commit, `game/server/persistence.js`
— журнал/checkpoint. Команды идут через `POST /api/command`, результат — через
`/api/command-state`; `/api/snapshot` от браузера отвечает 409. Подробности:
[docs/MP_IMPLEMENTATION.md](docs/MP_IMPLEMENTATION.md), проверки —
[docs/MP_VALIDATION.md](docs/MP_VALIDATION.md). Старые разделы AGENTS.md о
хосте-авторитете (если встретятся ниже) читать как историю.

## Неактивная партия удаляется через 30 секунд (правило заказчика, 2026-10-29)

Партия, в которой нет ни одного подключённого игрока, живёт **30 секунд** и
удаляется целиком — лобби, worker комнаты и её каталог в `STATE_DIR`
(`game/server/server.js`: `INACTIVE_TTL`, `sweepInactiveLobbies`,
`closeLobby`, `stopRoom`).

- «Подключён» — живой SSE или запрос игрока внутри окна. Скрытая вкладка
  держит SSE, поэтому фон идущую партию не убивает; F5 успевает вернуться.
- Уход последнего игрока через `/api/leave` закрывает партию сразу, не ждя
  окна. Это освобождает `MAX_ACTIVE_ROOMS` (по умолчанию 1): иначе новая
  партия получает `server_capacity` («на сервере уже идёт другая партия»), а
  после рестарта Node старая комната поднимается из checkpoint и блокирует
  сервер навсегда.
- Не возвращать `lobbies.delete` без остановки комнаты: это и был баг.
- Приёмка: `node game/tools/tests/mp-inactive.js` (окно, живой SSE, уход
  последнего игрока, старт следующей партии). Плюс `mp-acceptance.js`,
  `mp.js`, `node --test game/tools/tests/*.test.js`.

## 3D-модели: только живой Blender через MCP

**Правило заказчика (2026-10-12): 3D-модели делаются только и исключительно в
УЖЕ ЗАПУЩЕННОМ Blender, через сокет аддона blender-mcp. Headless для создания
формы запрещён.**

Сборка идёт в том Blender, который открыт у заказчика: модель появляется у него
во вьюпорте сразу, итерации по форме идут на глазах, Blender не перезапускается.

### Как подключиться

Аддон стоит, сервер слушает `127.0.0.1:9876`. Клиент лежит в проекте копией
(`art/props/shovel/tools/blmcp.py`, `art/characters/villager/tools/blmcp.py`) —
копируй его в новый проект. В трёх старых проектах тот же файл назван
`mcp.py` — см. docs/STRUCTURE.md §7.

```bash
PY=/Users/hermmoment/.dsh/profiles/desktop/node_modules/dsh-blender/.venv/bin/python
$PY tools/blmcp.py info                      # что открыто в Blender
$PY tools/blmcp.py run tools/build_live.py   # собрать/пересобрать
$PY tools/blmcp.py shot renders/live_view.png # скриншот вьюпорта
$PY tools/blmcp.py code "print(bpy.app.version_string)"
```

Если сокет замолчал (`ConnectionRefusedError`, а окно Blender живо) — заказчик
жмёт `N` → вкладка **Blender MCP** → **Connect to MCP server**.

### Что нельзя делать в живой сессии

1. **Не звать `bpy.ops.wm.read_factory_settings`** — это сносит файл заказчика
   вместе со всеми его сценами. Признак фонового режима — **только
   `bpy.app.background`**, никогда не `bpy.context.window is None`.
2. **Не сохранять чужой файл.** `.blend` для отдачи — только копией
   (`save_as_mainfile(copy=True)`).
3. **Работать в своей сцене и со своим префиксом имён** (`lc_`, `vg_`, `vh_`),
   чистить только свои объекты и материалы. Чужие сцены не трогать.
4. **Геометрию держать в чистом Python** (`art/buildings/lumbercamp/tools/building.py`,
   `art/props/shovel/tools/shovel.py`), а MCP использовать как способ запуска.
   Иначе форму не измерить и не повторить.
5. **Сбрасывать кэш модулей** перед `run`: Blender — долгоживущий процесс, без
   этого правка кода не подхватывается и сборка молча идёт старым кодом.

### Где headless всё ещё нужен

Пакетный рендер и пост-обработка **уже замороженной** геометрии, когда живой
сессии нет физически. Создание и правка формы — только живая сессия.

## Посадка построек в игре: зазор и середина (правило заказчика, 2026-10-13)

Основание постройки — цоколь **вместе с крыльцом, приступком и прочими
деталями у земли** — стоит по середине пятна и не вплотную к его краям: между
основанием и краем остаётся зазор, чтобы две постройки могли стоять рядом.
Крыша свешиваться за пятно может: она в воздухе, и её силуэт в пятно не
загоняют.

- Зазор: `mapgen2/js/buildings.js` → `BASE_MARGIN = 1/3` клетки по длинной
  стороне пятна, крупность спрайта — `siteMul(сторона) = fitMul(сторона) ×
  MARGIN_K`, где `fitMul = 1 − 2·BASE_MARGIN / сторона`, а `MARGIN_K = 0.92` —
  **общая поправка минус 8 %** (пятно 4 × 3 → 0.7667, пятно 3 × 3 → 0.7156).
  Число живёт в упаковщике атласа, рядом с атласом.
- Середина: считается по **наземному контуру**, а не по модели, — у ратуши
  сбоку крыльцо, и по модели основание стоит не по середине. Контур меряет
  упаковщик (`mapgen2/tools/pack_townhall.py`) по пикселям кадра и пишет
  в атлас полем `ground`; рендер сдвигает точку опоры на его середину. Контур —
  это **всё, что стоит на земле**: цоколь, крыльцо, приступок, двор (брёвна,
  солома). Где каменный цоколь идёт не сплошной полосой, пиксельный замер врёт
  (он видит только ближний к камере край основания), и контур считается **по
  модели** — так у лагеря лесоруба
  (`art/buildings/lumbercamp/tools/pack_lumbercamp.py`) и у стартового дома,
  который в игре дом жителя
  (`art/buildings/starter_house/tools/pack_atlas.py`; разбор и числа — в его
  README, раздел «Почему `ground` посчитан по модели»).
- Новую постройку без этого не принимают: `node mapgen2/tools/place.js` сам
  меряет контур по пикселям атласа и проверяет и зазор до всех четырёх кромок,
  и совпадение середины контура с серединой пятна. У построек с модель-мерным
  контуром (дом, лагерь) он вместо этого сверяет по пикселям ВИДИМУЮ часть
  основания — она тоже обязана стоять серединой в середине пятна.

## Поправка −8 % — общая для всех построек (правило заказчика, 2026-10-14)

Заказчик: **«отступы нижней площади модели от краёв её площади должны быть
такими же, как у ратуши»**. Ратуша с 2026-10-13 стоит на 8 % мельче правила, и
эта поправка перестала быть её исключением: дом жителя и лагерь лесоруба
получили то же самое (`siteMul(3) = 0.7156`), а атласы — поле `mul`, равное
`siteMul`.

Отступ в клетках при этом не одинаковый у всех (он растёт вместе с пятном:
0.40..0.50 у ратуши, 0.43..0.47 у дома, 0.48..0.53 у лагеря) — один масштаб на
обе оси не даёт сделать его равным на разных пятнах. **Видимый** отступ, тот
что меряется по пикселям кадра, у всех построек выходит одинаковым с точностью
0.03 клетки; остаток — оттого, что основание лагеря занимает 2.86 клетки из 3,
дома (стартового, см. ниже) 2.98 из 3, а ратуши 4.05 из 4. Убирается он
моделью, а не масштабом.

## Перед постройки — вправо-вниз (правило заказчика, 2026-10-15)

Заказчик: **«все здания и сооружения должны смотреть передней частью вправо
вниз»**. В игре (изометрия 2:1, клетка уходит вправо-вниз) это значит: дверь
дома, крыльцо ратуши и рабочий двор лагеря смотрят на камеру, а не в спину
зрителю. Число одно на всех — `Buildings.FACE_ROT = 90`
(`mapgen2/js/buildings.js`, там же разбор, почему 90, а не 0). Берут его:
деревня партии (`session.js` → `homeSpot`/`neighbourSpot`), ручная постановка
в генераторе (`app.js`, чипа 90° выделена по умолчанию) и «поставить все три».

Почему это понадобилось: ратуша игрока всегда стояла под 90°, а дом и лагерь
разворачивались «лицом к деревне» (`faceRot`) — и в половине сидов выходило
180°: дом встречал игрока глухой стеной, а лагерь прятал двор за собственным
навесом. `faceRot` из движка убран: правило отменяет выбор поворота по месту.
Заодно исправлен `Buildings.faceDir(rot)` — он был зеркальным по X, и житель
выходил из дома с задней стены.

## Деревня на старте партии (2026-10-14)

В начале игры на карте появляется не только ратуша: рядом с ней встают **дом
жителя**, **лагерь лесоруба** и **военный лагерь** (`mapgen2/js/session.js` →
`VILLAGE`, место выбирает `Buildings.neighbourSpot`: пятно к габариту деревни;
поворот у всех один — `FACE_ROT`, правило выше). Обе оболочки зовут один и тот же код,
поэтому деревня у игры и у генератора одна. Житель выходит из дома — из клетки
перед дверью (`Buildings.frontSpot`).

Постройка — это **тип** (`b.type`): `townhall`, `house`, `lumbercamp`,
`barracks`, `warcamp`. Тип выбирает атлас (рендер), пятно и крупность (посадка). Постройка без типа
считается ратушей. Новый тип — строка в `Buildings.TYPES`, тег `<script>` в
обеих оболочках и запись в загрузке (`mapgen2/js/app.js`, `game/js/boot.js`).

Модель дома жителя заказчик заменил 2026-10-14: **«добавь starter house вместо
того дома жителя, который сейчас в игре; именно в игре замени модельку; сами
модели удалять не надо»**. Сделано без нового типа: тип `house` остался, а его
атлас теперь `mapgen2/assets/starter_house/`
([art/buildings/starter_house](art/buildings/starter_house/README.md), пятно
**2 x 3**, один вариант, 4 поворота). Прежний дом жителя
([art/buildings/villager_house](art/buildings/villager_house/README.md)) и его
атлас `mapgen2/assets/house/` лежат на диске целыми, но страница их не грузит.
Возврат прежней модели — строка `dir`/`meta` в `TYPES` (`mapgen2/js/buildings.js`)
и тег `<script>` в `mapgen2/index.html` и `game/index.html`.

## Тени у зданий убраны (правило заказчика, 2026-10-17)

Заказчик: **«убери тени у зданий»**. У всех построек игры — ратуши, дома
жителя, лагеря лесоруба, казармы и военного лагеря — контактного пятна под
силуэтом больше нет. Делается
это в `compose.py` ключом `--no-shadow` (он есть и в копиях скилла, и в
`art/buildings/townhall/tools/compose.py`), а не правкой атласа руками: кадр
собирается тем же пайплайном, что и раньше.

Числа атласов от снятия тени НЕ меняются: `anchorX/anchorY`, `ground`, пятно,
`mul` те же, спрайты стоят на карте там же, где стояли. Проверено сверкой
старого и нового атласа: отличия — только пиксели пятна (у дома и лагеря) и
пиксели, которые пятно затемняло по краю силуэта (у ратуши).

Побочное следствие: строка «ТЕНЬ» стиль-гейта
(`4tox-lowpoly-3d/scripts/audit.py`) у построек теперь падает намеренно — гейт
требует мягкое пятно под силуэтом, а его больше нет. Остальные строки гейта в
силе. У природы (деревья, камни, кусты) тень осталась.

## Кусты и трава не мешают ставить здания (правило заказчика, 2026-10-17)

Заказчик: **«сделай так, чтобы кусты и трава не мешали располагать здания, то
есть чтобы препятствием для здания в момент размещения или перемещения были
только деревья и другие здания»**; на уточняющий вопрос про камни выбран
ответ «деревья и камни, как у жителей».

Отсюда два списка в `mapgen2/js/buildings.js`:

- **помеха** (`Buildings.obstacle`) — дерево и камень крупнее гальки: место не
  годится, пока не разрешена расчистка; отказ словами «мешают деревья и
  камни: N»;
- **украшение** (`Buildings.decor`) — куст, трава, цветы, камыш, галька: не
  помеха НИКОГДА, даже в строгом режиме и в правке.

Правило то же, по которому ходят жители (`Villagers.solidObject`): что мешает
ходьбе, то мешает и стройке.

С 2026-10-26 место проверяется ещё и по ЖИВЫМ ЖИТЕЛЯМ (`canPlace(...,
{villagers})` — дом в клетку человека не встаёт) и по ВЫХОДАМ действующих
построек (`opts.protectExits`): постановка, поворот или перенос, запирающие
все выходы соседней постройки, — отказ словами. Те же правила у хоста и у
клиента; поворот проверяется так же, как перенос (`checkAt`).

Украшение при этом не остаётся под домом — оно **сминается**
(`Buildings.settle` → `crushDecor`, пятно плюс клетка вокруг). Куст из передней
половины пятна по земле ближе камеры и рисуется поверх стены. Сминается в
момент, когда постройка ВСТАЛА: постановка в генераторе и «Применить» в игре
(`game/js/play.js`). Ведение дома за курсором мира не меняет — иначе «Отменить»
возвращало бы дом на выкошенный луг.

Приёмки: `mapgen2/tools/place.js` (заросшее пятно годится и в строгом режиме,
дерево — отказ словами), `mapgen2/tools/game.js` (в правке куст не запрет),

деревьев в мире не убывает).

## Мелочь не видна под зданием, которое ставят или ведут (правило заказчика, 2026-10-18)

Заказчик: **«сделай так, чтобы когда размещалось здание, кусты и трава, то есть
всё что не мешает размещению здания, исчезало из-под здания и вокруг здания на
одну клетку от здания; а то сейчас здание спавнится или я его переставляю куда-то
и внутри него отображается куст или трава»**.

Правило 2026-10-17 сминало мелочь только в момент, когда постройка ВСТАЛА, а
ведение дома за курсором мир не трогало (иначе «Отменить» вернуло бы дом на
выкошенный луг). Отсюда дыра: дом, который ведут или только что поставили и ещё
не применили, уже стоит в новом месте, а куст под ним — в мире, и по земле он
честно ближе камеры, поэтому рисуется поверх стены: куст «внутри дома».

Теперь мелочь прячет **отрисовка**, а не мир:

- `Buildings.coverCells(b, yard)` — клетки, которые постройка закрывает: пятно
  плюс `Buildings.YARD` (одна клетка, то же число, что у расчистки) вокруг;
- `Renderer.coverMask()` (`mapgen2/js/render.js`) — те же клетки по всем
  постройкам **и по призраку** под курсором; объект-украшение
  (`Buildings.decor`) из закрытой клетки в обход `eachSprite` не попадает.

Отсюда всё сразу: под ведомым домом, под поставленным и ждущим «Применить», под
призраком в генераторе мелочи не видно, а мир про неё не знает — «Отменить»
возвращает дом на целый луг, и мелочь возвращается сама, потому что её не
убирали. Деревья и камни не прячутся никогда: они помеха, место под ними и не
годится, а призрак над деревом честно показывает, что тут будут рубить.

Пропуск живёт в `eachSprite`, а не в `drawObjects`: этот обход один на экран и на
экспорт PNG, поэтому «на карте нет, а в выгрузке есть» разойтись не может.

Приёмки: `mapgen2/tools/place.js` (под призраком мелочь в мире есть, а на кадре
её нет; наведение мыши мир не меняет), `game/tools/menu.js` (то же под ведомым и

## Кнопка срабатывает, даже нажатая у самой кромки (правило заказчика, 2026-10-19)

Заказчик: **«когда нажимаешь на кнопку в интерфейсе, наводясь на самый её
край, анимация нажатия есть, а самого нажатия не происходит — игра не
начинается, карта не меняется, житель не нанимается; вообще всех кнопок
касается»**.

Причина в самой анимации. Кнопка утапливается на `:active`
(`transform: translateY(var(--press))`): коробка уезжает вниз на 2–7px, и
вместе с ней уезжает область попадания. Курсор, стоявший у верхней кромки,
оказывается уже НАД кнопкой, отпускание достаётся родителю, `click` до кнопки
не доходит. Состояние `:active` при этом живо, пока жива кнопка мыши, поэтому
нажатие видно — и только. Короткий клик (быстрее перехода `.09s`) проскакивает
раньше, чем кнопка уедет, и потому «в тесте работало».

Лечится не отказом от утапливания, а невидимой накладкой
`button:active::before` (`game/css/base.css`): у нажатой кнопки появляется
полоса высотой в ход, лежащая на месте, с которого кнопка уехала. Псевдоэлемент
— часть самой кнопки (отдельной целью события он не бывает), поэтому отпускание
в полосе снова попадает в неё; полоса живёт только пока кнопка нажата и ничего
не рисует. Ход и высота полосы считаются от ОДНОЙ переменной `--press`, заданной
у каждой кнопки: `play-btn` 7px, `wood-btn` 4px, `icon-btn` 3px, `hire-btn` 3px,
`mini-btn` 2px, `dice-btn` 4px, `size-card` 2px. Новую кнопку с утапливанием
заводить только так: `--press` и `translateY(var(--press))`, иначе накладка
перестанет совпадать с ходом.

То же у генератора карт — `mapgen2/css/style.css`, `--press: 1px`.

Приёмки: `game/tools/menu.js` — `edgeClickOn`, нажатие 1px от верхней кромки с
паузой 240 мс (дольше перехода): «Играть», кубик, карточка размера, зум, «Меню»,
«Продолжить», «Новый остров», «Нанять», «Применить», «Повернуть»; короткий
`clickOn` эту поломку не ловит и зелёный на сломанном. `mapgen2/tools/game.js` —
кубик панели тем же нажатием.

## Тренировка воинов и военный лагерь (правило заказчика, 2026-10-22)

Заказчик: **«в казарме они должны не наниматься а треннироваться»**, «в
интерфейсе казармы нажать тренировать по свободному жителю», «тренировка воина
должна идти 5 секунд», «когда превратился в воина, выйти из казармы уже в
облике воина и направиться в военный лагерь», «пока не вышел — модель обычного
жителя», «под каким бы углом не стояла казарма, житель шёл именно ко входу»,
«заступив на территорию, а не просто встав рядом, раствориться».

Как это устроено, чтобы не переизобретать:

- **Казарма — не рабочее место.** `Buildings.WORK.barracks` пуста,
  `workSlots(barracks) === 0`; в `TYPES` есть `trainingSlots` и таблица
  `Buildings.TRAIN` (три места). Наём в казарму запрещён: `Session.canHire`
  отвечает «в казарме тренируют, а не нанимают».
- **Правда о тренировке — поля жителя**, а не список у казармы: `v.trainee`,
  `v.trainingAt`, `v.trainT`, `v.warrior`, `v.warcamp`. `v.employer` остаётся
  только у лесоруба. `v.training` старого «рыцаря во дворе» больше нет.
- **Вход — по двери, а не по середине фасада.** Дверь казармы сдвинута от
  центра, поэтому точку входа считает `Buildings.entrance` (дверь в осях модели
  × `mul`, поворот через `faceDir`), и точка `in` лежит ВНУТРИ пятна, `out` —
  снаружи. Тренировка начинается только после заступа на территорию.
- **Пять секунд** — `Session.TRAIN_TIME`, отсчёт начинается на пороге, а не по
  нажатию кнопки. Пока идёт и учится — атлас жителя; растворение/проявление —
  `Villagers.vanishT` / `emergeT`, `Villagers.visibility`, `v.hidden`.
  `Renderer.villagerSet` переключает атлас по `v.warrior`, а не по
  `v.employer`.
- **Военный лагерь — пятно 5 x 5, модель 2 x 2.** Для посадки/правки/подсветки
  занято всё пятно (`Buildings.cells`); для ходьбы воинов открыто кольцо из 21
  клетки (`patrolCells`), четыре центральные закрыты (`modelCells`). Путь
  внутри считается по карте, где за кромкой всё закрыто
  (`Villagers.campSolid(..., true)`), поэтому за лагерь выйти нельзя. Снос
  лагеря запрещён (`Buildings.EDIT.warcamp.remove = false`).
- **Лагерь стоит в деревне на старте** (`Session.VILLAGE`), атлас подключён в
  двух `index.html` и `game/js/boot.js`.

Приёмки: `node mapgen2/tools/game.js` — все четыре поворота входа, пять секунд
(4.8 ещё ученик, 5.1 воин), растворение, выход воином, пятеро воинов 120 с
ходят по 21 клетке и ни разу не заступают на модель; `node mapgen2/tools/
place.js` — атласы пяти типов и деревня из четырёх построек; `node
game/tools/menu.js` — панель «Тренировать», счётчик «воины N · тренируются K /
3», порядок групп, живой путь воина до лагеря; `node mapgen2/tools/
lumbercamp-move.js` и `node mapgen2/tools/lumberjack.js` — лагерь лесоруба не
сломан.

## Обводка построек не жирнеет при отдалении (правило заказчика, 2026-10-24)

Заказчик: **«когда отдаляешь обводка спрайтов сооружений становится слишком
жирной»**. Цветной контур вокруг спрайта постройки (`Renderer.drawSpriteOutline`
→ `spriteEdge`) задан в пикселях ЭКРАНА — 1.4 у постройки, 1.1 у жителя (он
обведён цветом всегда, см. раздел ниже) — и обязан быть такой толщины на
любом зуме.

Почему жирнел: кайма режется в пикселях кадра (силуэт спрайта минус его
уменьшенная копия), а переводит её в экранные масштаб самого спрайта
`box.dw / spr.sw`. В формулу было подмешано ещё и отношение пикселей кэша
земли, `cam.zoom / cachePx`, — а зум уже сидит в масштабе спрайта. Он входил
второй раз, и на отдалении кайма росла как z²: при стартовом отдалении выходило
3–4 пикселя вместо 1.4, при приближении — 0.6 вместо 1.4. Теперь перевод один:
`px = screenPx / (box.dw / spr.sw)`, снизу ограниченный одним пикселем кадра
(тоньше силуэт не режется; на самом крупном зуме кайма ~0.8).

Каёмочных холстов на спрайт — не больше шести (`EDGE_CACHE`): при плавном зуме
толщина пробегает десятки значений, и на каждое приходился бы холст размером с
кадр (~0.9 МБ у ратуши).

Приёмка: `node mapgen2/tools/game.js` — кайма меряется по пикселям на шести
зумах (предел отдаления, 16, 24, 40, 80, предел приближения): 0.6..2.0 пикселя
на сторону, ни одного пикселя за кадром, холстов не больше шести.

## Игра не встаёт: ни в фоне, ни в меню (правило заказчика, 2026-10-24)

Заказчик: **«игра ставится на паузу если ухожу с вкладки на другую вкладку или
в другое окно либо если захожу в меню; а нужно чтобы никогда не
останавливалась»**.

- **Часы мира — стенные, не кадровые.** `game/js/boot.js` → `advance(now)`:
  каждый, кто проснулся (кадр, таймер скрытой вкладки, `visibilitychange`,
  `focus`, `pageshow`, `resume`), догоняет весь прошедший отрезок шагами
  `SIM_STEP = 0.05 с`. rAF в скрытой вкладке замирает, `setInterval` редеет до
  раза в секунду (в глубоком фоне — до раза в минуту), а мир догоняет
  пропущенное. Догон ОГРАНИЧЕН: 8 мс стенных на видимую вкладку, 25 на
  скрытую, остаток долга ждёт следующего вызова; долг больше 120 с честно
  выбрасывается и показывается словами. Замер: 10 минут фона на 192-й карте с
  200 существами — первый вызов 26 мс, дальше без блока больше 100 мс; до
  патча тот же отрезок был одним синхронным блоком ~1 с.
- **Экран «Меню» — не пауза.** `Play.pause()` больше не выключает
  `state.running`: он только ставит `mode = 'paused'` (игровой ввод молчит,
  `isPlaying()` false) и показывает счётчики. Жители работают, бой идёт,
  «Новый остров» и «В главное меню» остаются кнопками этого экрана.
  `Play.resume()` не включает `running` насильно: если ратуша пала за
  открытым меню, мир остаётся стоящим.
- **Главное меню тоже не останавливает начатую партию.** `Play.showInMenu()`
  не гасит `running`; заставка за меню — тот же мир, он продолжает жить.
  Стоит только время до первой партии и исход боя. Экран итога поверх
  главного меню не показывается (`boot.js`, обработчик `defeat`).
- **Интерфейс:** заголовок «Пауза» заменён на «Меню», под ним строка «игра не
  останавливается»; `#pause`, `Play.pause/resume`, `Hud.openPause` остались
  именами в коде.
- **Сеть:** хост больше не обязан держать вкладку активной — время догоняется.
  Снапшоты в глубоком фоне браузер всё равно может редить (таймеры), это
  ограничение браузера, а не остановка мира.

Приёмка: `node game/tools/menu.js` — 5 секунд мира за открытым меню и живой
счётчик на доске, рождение на 30-й секунде за меню, заморозка страницы
(`Page.setWebLifecycleState`) и догон всего отрезка, время в главном меню;
проверки «в паузе время стоит» заменены. Браузерная приёмка движка
(`node mapgen2/tools/game.js`) не трогается: правка только в оболочке игры.

## Мультиплеер: транспорт, старт и цена ошибок (правило 2026-10-24)

Заказчик: **«мультиплеер работает очень коряво… у друзей лагало… весь остров
пропал и осталась только вода и стало 3 фпс»**. Причины были не в правилах
игры, а в транспорте и обновлении клиента; трогать их обратно нельзя.

- **Старт — только кнопкой хоста.** `POST /api/start` (в UI — «Начать игру»,
  видна только хосту) после того, как все нажали «Готов». Автостарт «как только
  все готовы» закрывал лобби на трёх, пока третий ещё открывал ссылку.
  `startBlock`/`lobby.canStart` — единственный ответ «можно ли начинать».
- **Снимок — `mapgen2/js/serialize.js`.** Поля: `seq`, `t`, `seed`, `size`,
  `towns`, `buildings`, `villagers`, `objectTotal`, `removed` (hex-битовая
  карта убранного), `notes` (ответы на команды). Массив `removed` — только
  обратная совместимость; в сеть его не возвращать: он растёт с каждой
  срубленной травинкой.
- **Хост шлёт не по `setInterval`, а из `Play.tick`** (`netSend`): база 80 мс,
  и только когда предыдущий POST завершился. Если круг дольше 420 мс,
  интервал сам растёт до 200 мс (`state.netEvery`), чтобы хост не забивал свой
  канал и у друзей не рос пинг. Круг до СВОЕГО сервера — loopback и о сети
  друга не говорит; настоящий сигнал — `queue` в ответе на снимок (см.
  «Поток сжат, а пинг честный» ниже). Так при медленной сети редеют свежие
  кадры, а не копится очередь устаревших. Клиент применяет только
  `seq > netSeq` и сглаживает позиции жителей между снимками.
- **Клиент сверяет, а не пересоздаёт.** `Serialize.apply` переиспользует
  объекты по id; `renderer.setBuildings(list, {minimap:false})` на обычном
  снимке. Миникарта — только при изменении состава/места построек или рубки
  (`removedChanged`), холст обзора переиспользуется. Версия — `minimapVersion`,
  по ней HUD решает, перерисовывать ли обзор.
- **Сервер** (`game/server/server.js`): SSE пишется одной строкой на событие,
  `res.socket.setNoDelay(true)`, для снимков `opts.drop` при
  `writableLength > 256 КБ` (пропуск безопасен — следующий снимок абсолютный),
  `/api/snapshot` отвечает хосту до рассылки. Любой запрос игрока обновляет
  `lastSeen`; хост считается потерянным только если от него нет ни SSE, ни
  снимков, ни heartbeat `GET /api/ping?code&token` дольше
  `HOST_GRACE = 60 с` (8 с хватало, чтобы живая партия получала «хост
  потерян» на одном долгом кадре). Хост шлёт heartbeat из `Play.tick` раз в
  2.5 с.
- **Команды** (`Net.command`): очередь по одной, номер `n` растёт по часам.
  Выполняет команды ОДНА точка — `Play.ingestCommands` из ответа снимка,
  отсортированного по серверному `sn`; SSE только будит снимок. Дедупликация —
  пара `(from,n)`; `cmdAck` двигается после решения. Результат
  `applied|rejected|expired` хост шлёт в `cmdDone`, сервер отдаёт его
  `/api/command-state`, клиент ждёт конечный результат, а не HTTP 200.
  Постройка клиента списывает брёвна у **его** деревни (`buildPrice`,
  `towns[who].logs`), а не у хоста. С 2026-10-26 серия домов — одна
  атомарная команда `buildLine`.
- **Войска — у каждого свои (правило 2026-10-24).** Панель «Войска»
  (`hud.js` → `refreshSquad`) собирает группы по `state.playerOwner`, а не по
  жёсткому 0: в сети это номер деревни игрока. `Army.groups` отбирает по
  владельцу и воинов, и сами лагеря/дворы казарм, иначе гость видел дружину
  хоста, а чужой лагерь занимал строку. Приказ и «Стоп» гостя уходят хосту
  командой с его owner; «Стоп» без выбора у хоста тоже снимает приказы только
  со своих (`Play.stopArmy` → `ownWarriorIds` + `Army.wardens`). Одиночная
  партия после выхода из сети сбрасывает `playerOwner` в 0 (`Play.start`).
- **Уход хоста** — `host-left`, но клиента НЕ выкидывает в меню: мир остаётся
  на экране последним кадром, бейдж говорит «нет связи». Вернулся — `host-back`
  продолжает партию; не вернулся — игрок сам откроет «Меню». Уход обычного
  игрока — `peer-left`, без остановки партии. Всплывашек в сети нет вовсе
  (правило 2026-10-24, раздел ниже) — только бейдж.
- **Приёмка:** `node game/tools/mp.js` — явный старт и третий игрок, формат
  снимка, сохранение объектов/выбора, отсутствие пересборки обзора, счётчик

### Поток сжат, а пинг честный (правило 2026-10-25)

Заказчик: **«мы каждую игру сталкиваемся с тем, что игра лагает и у друзей
огромный пинг»**. Сначала замерили, а не стали верить: снимок мира на 192-й
карте — **5,2 КБ**, 12,5 кадров в секунду, то есть **~523 Кбит/с на каждого
друга** (замер `Network.dataReceived` в Chrome). Канал вверх у домашнего
интернета общий и узкий; два-три таких потока заполняли его, роутер ставил
пакеты в очередь — и круг до сервера рос до сотен миллисекунд, хотя игра
считает быстро. Это bufferbloat, а не «медленный сервер».

- **SSE сжимается gzip в потоке.** `server.js` → `openEventStream`: при
  `Accept-Encoding: gzip` ответ получает `Content-Encoding: gzip`, и все
  записи идут через `zlib.createGzip({ level: 1, flush: Z_SYNC_FLUSH })`.
  Уровень 1 даёт 606 байт против 658 у 9-го, а стоит копейки. `Z_SYNC_FLUSH`
  обязателен: без него zlib копит блок и «мгновенные» события приезжают
  пачками. На том же наборе снимков провод стал **~20 Кбит/с вместо 523** —
  в 26 раз меньше (соседние кадры похожи, словарь и работает).
- **Пишут только через `streamWrite(res, …)`.** Смешать сырой текст с
  gzip нельзя: `send`, `broadcast`, `retry:` и heartbeat `: ping` идут одним
  путём. Заголовки, обёртка и `setNoDelay` — в одном месте, с первого байта.
  Без `Accept-Encoding: gzip` клиент получает обычный SSE (проверено).
- **`Vary: Accept-Encoding`** обязателен: иначе прокси отдаст сжатый ответ
  клиенту, который его не просил.
- **Хост редеет по очереди друзей, а не по loopback.** Сервер кладёт в ответ
  на снимок `queue` — `writableLength` самого отстающего потока (в сжатых
  байтах). `play.js` → `NET_QUEUE_HIGH = 24 КБ`, `NET_QUEUE_LOW = 4 КБ`:
  выше — `netEvery` растёт, ниже — возвращается к 80 мс. Круг до СВОЕГО
  сервера — 2–7 мс и о сети друга не говорит ничего; старый порог `420 мс`
  поэтому не срабатывал никогда.
- **Пинг меряется сетевым стеком.** `net.js` → `ping` берёт
  `requestStart → responseEnd` из Resource Timing и отдаёт `ms`; разница
  `performance.now()` вокруг промиса осталась запасной (`msWall`). Раньше
  занятый кадром главный поток показывал честные 20 мс как «420 мс», и игрок
  шёл чинить интернет вместо окна. `measuredBy: 'network'` — признак, что
  число настоящее.
- **Снимок ВВЕРХ тоже сжимается.** В VPS-режиме (`--host` + Caddy) сервер
  стоит не на машине хоста: те же 5,2 КБ × 12,5 идут с домашнего интернета
  хоста на релей, это 520 Кбит/с вверх — тот же узкий канал. `start` несёт
  `snapGzip: true`; `net.js` → `snapshot` жмёт тело `CompressionStream('gzip')`,
  `readJson` принимает `Content-Encoding: gzip` (`maxOutputLength` 8 МБ), а
  ответ снимка несёт `gzip: true` — по нему приёмка видит, что браузер правда
  сжал. Нет `CompressionStream` или старый сервер — уходит обычный JSON.
- **Возврат в игру сбрасывает частоту снимков.** `Play.netWake` зовётся из
  `boot.js` на `visibilitychange`, `focus`, `pageshow`, `resume`: в скрытой
  вкладке браузер редеет таймеры, и круг вокруг POST врёт — хост зря уходил
  на 200 мс и оставался там после возврата. Настоящую забитую сеть очередь
  (`queue`) снова заметит.
- **Не возвращать:** несжатый SSE; `res.write` в обход `streamWrite`; снятие
  `Z_SYNC_FLUSH`; `ms` из одного `performance.now()`; порог частоты только по
  loopback-кругу; снимок вверх без gzip в VPS-режиме.

Приёмка: `node game/tools/mp.js` — раздел сжатия (тот же набор снимков едет
двум клиентам, с gzip и без; сжатый поток не застревает, весит меньше 40 %
исходного и вдвое легче несжатого; сжатое тело снимка сервер принимает, ответ
несёт `gzip: true`, обычное тело — тоже), темп 12 снимков/с у гостя при
видимом хосте (мир на эти секунды заморожен, чтобы не сдвигать следующие
проверки), ровные промежутки между кадрами, `measuredBy === 'network'` у круга
и `state.netGzip === true` у хоста. Плюс обязательные
`node mapgen2/tools/game.js` и `node game/tools/menu.js`.

### F5 и возврат в партию (правило 2026-10-24)

Заказчик: **«если перезагрузить страницу тебя не кидало в меню, а ты
продолжал играть в матче; и мог вообще продолжить играть, если тебя
выкинуло»**.

- **Сессия живёт в браузере.** `game/js/net.js` хранит `{code, token,
  playerId, hostId}` в `localStorage` под ключом вкладки (id вкладки —
  `sessionStorage`), поэтому F5 в той же вкладке находит свою партию, а две
  вкладки в одном браузере не затирают сессии друг друга. `leave`/выход в
  меню ключ удаляют; битый/просроченный ключ очищается после 403 от сервера.
- **Сервер отдаёт последний снимок.** `POST /api/snapshot` кладёт его в
  `lobby.lastSnapshot`; `GET /api/resume?code&token` возвращает `start`,
  `snapshot` и `seq`. `/api/join` после старта по-прежнему закрыт: возврат —
  только по своему токену.
- **Старт после F5 не применяется без снимка.** `Net.resume()` держит
  `resuming`: SSE-`start` откладывается в `pendingStart`, затем
  `/api/resume` приклеивает `snapshot` и только после этого `handleStart`
  запускает партию. Иначе хост поднял бы пустой остров.
- **Хост поднимает мир из снимка**, а не начинает заново:
  `Play.startNet` → `restoreFromSnapshot` (`Serialize.apply` с
  `smooth:false`), затем `normalizeResumedVillagers` (пути/цели сбрасываются,
  ученики и работники остаются при деле) и **`Serialize.hydrate`** — каждый
  житель собирается полным шаблоном `Villagers.blank` (speed, rng, anchor,
  счётчики) и накрывается полями снимка; груз, обучение, здоровье и приказ
  сохраняются. Без гидратации после F5 гражданский стоял без якоря, лесоруб
  давал NaN, воин падал на `v.rng`, а исключение убивало rAF-цикл. Часы
  рождения — на следующую границу, `nextBuildId` — выше старых id. Нумерация снимков продолжается с
  `snapshot.seq`; `/api/resume` для хоста сбрасывает `lastSnapSeq`.
- **Клиент** по снимку сразу ставит камеру на свою ратушу и не ждёт первого
  живого кадра. Если хост вернулся после `host-left`, его первый снимок
  вызывает `host-back` — клиенты снимают ожидание и продолжают.
- **Бут не показывает меню**, если есть сохранённая сессия: `boot.js` →
  `begin` сначала зовёт `Lobby.resumeSaved()`, при неудаче — обычное меню.
  `Lobby.resumeSaved` показывает экран лобби с «возвращаемся в игру…», чтобы
  не мигать меню.
- **Приёмка:** `node game/tools/mp.js` — F5 гостя (тот же город, стройка и
  казна) и F5 хоста (мир из снимка, маркер перенесённого дома, рубка, время),
  после чего гость снова в игре. Плюс `node mapgen2/tools/game.js`,
  `node game/tools/menu.js`.

## Управление не зависит от платформы (правило заказчика, 2026-10-24)

Заказчик: **«ей можно управлять только с мака; мои два друга на Windows не
могут редактировать здания, с трудом их ставят и вообще плохо управляется;
тупо ЛКМ не работает»**. Это были НЕ «Windows плохой», а три наши ошибки в
одном месте — обработке мыши. Все три воспроизведены мышью и клавиатурой в
headless Chrome (см. приёмки) и исправлены.

**1. Дрожь руки считалась перетаскиванием.** Порог был `CLICK_SLOP = 6` и
считался по **сумме** пройденного пути (`drag.moved += |dx| + |dy|`). Мышь на
Windows за полсекунды удержания уходит на 5–12 px — обычная рука, а не жест, —
и это читалось как панорама. Отсюда сразу все три жалобы: клик не выбирал
постройку, удержание не открывало правку, постановка срывалась. На маке
тачпад «тапает» почти без сдвига, поэтому там работало.

- `game/js/play.js` (и `mapgen2/js/app.js` для генератора): дрожь —
  `Math.hypot(clientX − x0, clientY − y0)`, то есть расстояние от ТОЧКИ
  НАЖАТИЯ, и оно только растёт; путь туда-обратно — ноль, а не «драг».
- `CLICK_SLOP = 8` — клик и постановка; `HOLD_SLOP = 18` — удержание
  (держать полсекунды труднее, чем кликнуть); `PAN_SLOP = 8` — камера едет
  только после порога, поэтому дрожащий клик не уводит карту из-под курсора.
- Удержание больше не прыгает домом: захват пересчитывается по ТЕКУЩЕЙ клетке
  (`take = cell − b.x`), `editFollow` ставит дом ровно туда, где он стоит.
  Ограничивать захват пятном нельзя — именно ограничение и давало прыжок на
  клетку, когда рука дрогнула за кромку.
- Отпускание ЛКМ ставит дом **до** проверки «это драг, а не клик»
  (`play.js`: ветка `state.edit.mode === 'move'` стоит выше `wasDrag`). Иначе
  дрожащее удержание (9–18 px, то есть ровно случай Windows) открывало правку,
  а отпускание съедалось как «перетаскивание»: дом оставался «в руке» и ехал
  за курсором без нажатой кнопки. Раньше это пряталось за тем, что первый
  `pointermove` при ведении обнулял `drag`; если игрок отпускал кнопку, не
  сдвинув мышь, обнулять было нечему.
- Потерянное отпускание (Alt+Tab, меню «Пуск», уход за окно) больше не
  оставляет камеру и дом «в руке»: `blur`, `pagehide`, `visibilitychange` и
  `pointercancel` закрывают жест. На `pointermove` состояние кнопки НЕ
  проверяется намеренно: у синтетических событий приёмки `buttons` бывает 0 при
  нажатой кнопке (так двигают дом в `game/tools/menu.js` и здания в
  `mapgen2/tools/place.js`), и такая проверка ломала бы настоящий переезд.

**2. Буквы сравнивались с `e.key`.** На русской раскладке физическая `W`
приходит как «ц», `R` — «к», `O` — «щ», `T` — «е». Молчали `WASD`, поворот
постройки, войска, сведения о деревне — всё, что повешено на буквы.

- Новый модуль движка `mapgen2/js/keys.js`, подключается ОБЕИМИ оболочками
  (`game/index.html`, `mapgen2/index.html`) сразу после `rng.js`.
- `Keys.name(e)` берёт имя по ФИЗИЧЕСКОМУ месту (`KeyboardEvent.code`:
  `KeyW` → `'w'`, `Backquote` → `` '`' ``, `ArrowUp` → `'arrowup'`), `e.key`
  остаётся запасным вариантом без `code`. `Keys.typing(e)` — одна проверка
  «клавиша пришла в поле ввода» на все оболочки.
- Берут `Keys.name` все обработчики: `game/js/play.js` (WASD, R, O, H, C, V,
  F, N, Esc), `game/js/hud.js` (T, Esc), `game/js/menu.js` (R, Enter),
  `mapgen2/js/app.js` (B, Q/E, 1–3, R, G, F, V, `` ` ``, Delete).
- Новую горячую клавишу заводить только через `Keys.name`; сравнивать
  `e.key` с латинской буквой больше нельзя.

**3. Контейнеры HUD ели клики по карте.** В `game/css/hud.css` стояло
`#hud > * { pointer-events: auto; }` — целью мыши был КАЖДЫЙ прямой ребёнок
HUD: левый столбец, правый угол, полоса подсказок внизу, полоса клетки.
Пустое место между табличками и вокруг них съедало клик, и карта под ним не
получала ничего. На большом окне это незаметно, на ноутбуке с масштабом
Windows 125–150 % доля мёртвых полей доходила до **трети** экрана (замер:
1440×900 — 11.8 %, 911×512 — 32.6 %).

- Теперь `#hud > *` — `pointer-events: none`, а ловят мышь только настоящие
  цели: `#hud button`, `#hud .plaque`, `#hud .build-menu`, `#hud .place-bar`,
  `#hud .edit-bar`, `#hud .debug-drawer.open`, `#hud .minimap-frame`, поля
  ввода. `.hint-bar` и `.res-bar` — текст, мышь они пропускают всегда.
- После правки мёртвых полей 5.6 % на 1440×900 и 15.3 % на 911×512, и это
  ТОЛЬКО настоящие кнопки и обзор. `elementFromPoint` в середине полосы
  подсказок обязан вернуть `#view`.
- Не возвращать `#hud > * { auto }` и не заводить контейнеру `pointer-events:
  auto` «на всякий случай»: это и есть та самая дыра. Специфичность здесь
  ловушка — правило с `#hud` бьёт класс, поэтому исключения пишутся тоже с
  `#hud`.

**Правка постройки: удержание и кнопка, без двойного клика (уточнено
2026-10-26, раздел «Финальная стабилизация» в конце).** Двойной клик правку
БОЛЬШЕ НЕ открывает (INPUT-01): вся карта — один canvas, и доказать, что оба
клика были по одному зданию, нечем. Остались намеренное удержание (0.5 с,

(`#btnEdit`, `game/index.html` + `game/js/hud.js` → `Play.editSelected`).
Кнопка открывает полосу правки, но НЕ берёт дом в руки; ведение — «Двигать»

движковые), и она же стоит в подписи кнопки. Подсказка внизу говорит
«удержать (или «Править»)».

**Колесо.** `wheelDelta(e)` переводит `deltaMode` 1 (строки, Firefox) и 2

`clientWidth`.

## Завал не красит землю (правило заказчика, 2026-10-24)

Заказчик: **«у сломанных построек появляется какая-то тёмная хуйня, а её быть
не должно, просто модель должна смениться на тёмную»**.

Причина была в отрисовке, а не в атласе: у завала (`b.rubble`) слой участка
пекся отдельным художником `Renderer.bakeRubble` — выгоревшее пятно
`rgba(42,34,24,0.84)` с пеплом, углями и мягким затуханием к кромке, на всё
пятно плюс 0.42 клетки вокруг. Спрайт руины меньше пятна (стены обвалились
внутрь), поэтому пятно торчало из-под постройки тёмным ромбом — «тёмная
хуйня». Тень у построек снята ещё 2026-10-17, и это было единственное тёмное
пятно, которое отрисовка клала под дом.

Выгоревшее пятно убрали, но под ним нашлась вторая беда того же рода:
**участок**. Плоский слой травы вокруг постройки (`plotLayer`) под целым
домом почти не виден из-под спрайта, а под руиной открыт целиком — и
читается пятном вокруг обломков, какого бы цвета он ни был.

Поэтому теперь **у завала участка нет вовсе** (`Renderer.paintPlot` →
`if (b.rubble) return`): разрушенное место зарастает дикой травой, а о
разрушении говорит ТОЛЬКО модель — `Renderer.spritesFor(type, true)`
подставляет кадр из `mapgen2/assets/ruins/`. У целых построек участок
остаётся на месте, со всеми прежними правилами.

- `Renderer.bakeRubble` удалён, `PLOT_CORE`/`PLOT_APRON` вместе с ним;
- `paintPlot` не строит участок для завала; `plotLayer` печёт только дерн
  (`bakeTurf`) и зовётся только для целых построек; ключ слоя — пятно и
  разрешение кэша (атласа в ключе нет: дерн процедурный);
- если заказчику понадобится, чтобы САМА руина была темнее, это правка
  материалов модели (`char`/`ash` в `art/buildings/ruins/tools/ruin_*.py`),
  а не затемнение земли под ней: палитра руин проверяется стиль-гейтом.

Приёмка: `node mapgen2/tools/ground.js` — три сида, раздел «завал»:
`plotLayer` за 3 кадра ни разу не спрошен про завал (у целых — 3 раза), в
пятне завала 100 % зелёных точек, обугленных 0 %, средняя яркость ~162 (у
выгоревшего пятна было ~57). Плюс обязательные `node mapgen2/tools/game.js` и
`node game/tools/menu.js`.

## Леса вдвое больше, но не крупнее (правило 2026-10-24)

Заказчик: **«сделай так чтобы на карте генерировалось в два раз больше лесов,
не увеличивая средний размер леса; также сделай так чтобы леса распределялись
по карте также рандомно и естественно как сейчас но более равномерно»**.

Сделано в `mapgen2/js/worldgen.js` — тремя числами и одной сеткой, а не
перестановкой деревьев:

- **`FOREST_DETAIL = 1.15`** — поле леса в 1.15 раза мельче прежнего. Одного
  удвоения доли суши под рощи мало: на прежней частоте соседние пятна
  слипаются, и выходит вдвое больше ЛЕСА, а не вдвое больше ЛЕСОВ. На новой
  частоте те же 12 % суши дают 51 пятно вместо 25, средним 97 клеток вместо
  99 (256×256).
- **`FOREST_LEVELS = 5`** — порог поля леса не один на карту, а свой в каждом
  узле сетки 5×5 (`forestQuotas`). Прежний общий квантиль оставлял целые края
  острова без рощ: там поле в среднем ниже. Теперь в каждой области под рощи
  уходит одна и та же доля суши. Порог между узлами интерполируется
  билинейно, поэтому сетки не видно, а рваную кромку рощи по-прежнему рисует
  поле.
- **`FOREST_QUOTA_MAX = 0.68`** — сколько суши уходит под рощи при ползунке
  «Лес» на 100 %. Кривая `forestQuota` проходит через 0 (леса нет), 0.5
  (прежние 50 % ползунка — но рощ вдвое больше) и 0.68. Выше 0.68 нельзя:
  рощи занимают пол-острова, «в роще/вне рощи» перестаёт читаться, а проверка
  «деревья собираются в рощи» на максимуме падает.
- **Густота деревьев не тронута** (`placeObjects` прежний), поэтому деревьев
  на карте тоже вдвое больше — это следствие, а не отдельная правка.

Замер по 90 картам (5 размеров × 6 сидов × coast 0/0.5/1), `forestStats`:
рощ **×2.03**, средний размер пятна **×0.97**, доля суши под рощами **×1.94**,
cv по 4×4 плиткам **1.10 → 0.53**, пустых плиток **2.37 → 0.20**. По размерам
patch ratio 2.01..2.15, mean ratio 0.96..1.03.

Два побочных следствия, оба компенсированы:

- **Камни.** В клетке стоят либо дерево, либо камень; деревьев стало вдвое
  больше, и часть бросков камня не доходила до своей ветки. `rockDensity`
  умножен на `1 + 0.22 * p.forest` — при «без леса» поправки нет, на 50 %
  она держит число выходов на прежнем уровне.
- **Площадки под деревни.** `spawnSites` требует квадрат без деревьев и
  камней. После удвоения лесов строгий коридор «лес и камень в норме» сжался
  в один угол острова: `spawnSites` ставил 1–3 точки, и мультиплеер на
  несколько деревень падал с «остров не дал n площадок». Теперь коридоры
  расширяются не по длине списка, а по числу РАЗНЕСЁННЫХ точек (`pickSites`),
  и камень у площадки сохраняется: коридор «камень в норме» идёт раньше, чем
  «камня может не быть». На 64-й карте площадка — **7 × 7**
  (`spawnSiteSize`): 9 × 9 там 1/50 карты, и чистых квадратов после удвоения
  лесов почти не остаётся; на 96 и больше — прежние 9 × 9.

Приёмка: `node mapgen2/tools/shape.js` — раздел «лес: вдвое больше, средний
размер прежний, распределение ровнее»: на каждом размере пятен 1.7..2.35×,
средний размер ≤ 1.10×, доля суши ×1.6..2.3, cv ≤ 0.80 и не больше двух
пустых плиток; площадки под деревни находятся на всех coast. Плюс

mapgen2/tools/place.js`, `node mapgen2/tools/lumberjack.js`, `node

## Команда едет снимком, постановка терпит дрожь (правило заказчика, 2026-10-25)

Заказчик: **«у моего друга в игре огромный пинг… здания ставятся 30 секунд
спустя клик… иногда бывают проблески, когда здания ставятся быстрее…
возможно, здания не ставятся из-за проблем с управлением»**. Причин было две,
и обе наши.

**1. Команда ехала только по SSE хоста.** `/api/command` отвечал 200 и
отправлял событие в поток хоста. SSE — односторонний поток без подтверждений:
если у хоста он оборвался или подвис (мобильная сеть, VPN, прокси), снимки
продолжали идти POST-ом, а клик терялся молча — клиент получал 200 и ждал
постройку, которой никто не видел. Когда поток случайно оживал, накопленные
клики доезжали пачкой — отсюда «иногда быстрее».

- `game/server/server.js`: команда кладётся в `lobby.cmdQueue`; хост забирает
  её в **ответе на свой `POST /api/snapshot`** (поле `commands`), а
  подтверждает номером `cmdAck` в следующем снимке. Сервер чистит очередь по
  ack; повтор с тем же `n` не задваивается; `CMD_TTL = 15 с` не даёт копиться
  кликам пропавшего хоста, `CMD_MAX = 200` — памяти.
- `game/js/play.js`: у хоста больше нет слушателя `command` — один путь, один
  порядок. `netSend` кладёт `cmdAck` в снимок, а `commands` из ответа
  применяет через `applyNetCommand`. `restoreFromSnapshot` восстанавливает
  `state.netCmdLast` из `snap.cmdAck`: после F5 уже выполненные команды не
  лягут второй раз.
- `game/js/net.js`: `Net.command` ждёт ответ 3 с и делает 2 попытки (было
  6 с × 3: одна неудачная команда держала следующую до 18 с). Номер команды
  растёт по `Date.now()`, а не с нуля: после F5 гость снова может строить
  (раньше его `n = 1…N` были меньше старых, и хост молча отбрасывал их как
  повтор).

**2. Дрожащая постановка считалась панорамой.** Порог постановки был общий с
кликом — `CLICK_SLOP = 8`. На Windows обычный клик уходит на 9–12 px: дом
оставался в руке, камера чуть уезжала, игрок жал снова. Теперь у постановки
свой `PLACE_SLOP = 18` (как у удержания): дрожь до 18 px ставит дом и не
двигает камеру; настоящая панорама (>18 px) по-прежнему не ставит ничего.
То же у генератора (`mapgen2/js/app.js`, `PLACE_SLOP`, `moveSlop`).

Приёмки: `node game/tools/mp.js` — команда без единого SSE-потока у хоста
приходит в ответе снимка, повтор не задваивает, ack чистит очередь, после F5
гость снова строит; `node game/tools/menu.js`, раздел 14c — дрожащая
постановка 11 px ставит дом и не уводит камеру, панорама 44 px оставляет дом
в руке и двигает камеру. Плюс обязательные `node mapgen2/tools/game.js`,
`node mapgen2/tools/controls.js`, `node mapgen2/tools/place.js`.

## Патч стабилизации 2026-10-26

Заказчик передал единое задание на стабилизацию (P0/P1/P2). Ниже — принятые
правила; числа и подробности — в `research/patch-2026-10-26/`.

### Команды: один путь выполнения

- Хост выполняет команды ТОЛЬКО из массива `commands` ответа на свой
  `POST /api/snapshot`, отсортированного сервером по `sn`. SSE-событие
  `command` не выполняет команду, а только будит снимок (`netForce`), поэтому
  порядок команд одного игрока один и тот же при любом канале.
- Дедупликация — пара `(from,n)` (`state.netCmdApplied`), `cmdAck` двигается
  только после решения команды (`recordCommandResult`). `HTTP 200` на
  `/api/command` значит «в очереди», а не «дом построен».
- Результат команды: `applied | rejected | expired`. Хост шлёт `cmdDone` в
  снимке, сервер хранит его в `lobby.cmdResults` и отдаёт
  `GET /api/command-state`; клиент `Net.command` ждёт конечный результат.
  Просроченная команда получает `expired`, а не исчезает молча.
- Серия построек — одна команда `buildLine` с концами `{x,y,x2,y2}`; план
  считает хост через `Buildings.planLine`, покупка атомарна, повтор с тем же
  `n` не задваивает.

### F5 хоста: гидратация, а не «пустые» жители

Снимок — формат отрисовки. Хост после возврата собирает каждого жителя
`Villagers.blank()` (полные поля: `speed`, `rng`, `anchor`, счётчики) и
накрывает полями снимка (`Serialize.hydrate`). Путь и цель пересчитываются;
груз, обучение, здоровье и приказ (`orderX/orderY`) сохраняются. Служебные
поля в каждый кадр не добавляются. Восстановленный житель обязан иметь
`speed`, `rng`, конечные координаты и таймеры.

### Часы мира: догон с бюджетом

- Шаг `SIM_STEP = 0.05 с`, один бюджет на вызов: 8 мс видимая вкладка, 25 мс
  скрытая. Минимум один шаг за вызов, иначе тяжёлый шаг заблокирует долг.
- Долг ограничен `MAX_DEBT = 120 с`; всё, что больше, выбрасывается и
  показывается словами («мир пропустил N с»), а не молча ускоряется.
- `__game.clock.jump(ms)` сливает долг порциями по 8 мс с дедлайном 5 с:
  тестовый прыжок не вешает вкладку и не теряет время.
- Экран «Меню» и главное меню время не останавливают; у клиента время
  авторитетно у хоста, свой долг он не копит.

### Рождение: по деревням независимо

- Число жителей, дома и свободные места считаются ПО ДЕРЕВНЕ (воины и ученики
  входят в население), выбывший город не рождает, недоступный дом пропускается
  и ищется другой дом той же деревни.
- Временно занятая клетка не отменяет рождение, а откладывает его: повтор раз
  в 5 с в окне до следующей границы 30 с. Темп рождения (30 с,
  `min(floor(pop/2), свободных мест)`) НЕ изменён.
- id жителей не переиспользуются: диапазон `town.id*1000`, `town._vidNext`
  переживает F5.
- HUD показывает население/вместимость, время до заселения и причину задержки
  (`Session.birthStatus`).

### Поиск пути: бюджет, заготовки, индекс

- `findPath` не аллоцирует массивы на остров: заготовка живёт в мире, а
  «посещали ли клетку» — номер поколения (`gen`). Один поиск — не больше
  `N/PATH_DIV` клеток, весь кадр — не больше `N/FRAME_DIV` (`beginFrame` зовёт
  `Session.stepVillagers`).
- Упор в бюджет — не «пути нет»: житель повторяет попытку, а `planSkip`
  продолжает перебор деревьев с того места, где оборвался.
- Деревья ищутся по клеточному индексу (`treeIndex`), а не полным проходом с
  сортировкой на каждое планирование. «Отсюда к этому дереву дороги нет»
  кэшируется на дереве до смены версии карты.
- Аварийный `stepOut` бюджет кадра не тратит и груз не теряет.

### Работа и брёвна

- Один предикат свободного гражданского (`Session.freeCivilian`) для панели,
  одиночного и массового найма. «Заполнить вакансии» берёт своих свободных
  достижимых по длине пути (`Session.hireRank`), занятых не перетаскивает.
- Казна деревни: `logs + 4·(inTransit + lost) = 4·felled`. `lost` растёт на
  ходку при смерти носильщика, увольнении/переназначении с грузом и сносе
  лагеря; потеря видна словами, груз не дублируется. Сдача начисляется ровно
  один раз (`deposit` проверяет `v.carrying`).

### Бой: конфиг и темп

- Все числа — в `Combat.CONFIG` (старые имена — алиасы). Урон по юнитам и по
  зданиям разный; по зданию — свой интервал; первый удар по новой цели не
  раньше `windup`.
- Цель баланса: ратуша держит атаку пяти обычных воинов 15–25 с без защиты.
- Бить можно только то, до чего есть прямая; цель в закрытой клетке чужого
  пятна не бьётся (исключение — кольцо своего военного лагеря). Недостижимая
  цель не берётся повторно каждый кадр.
- «Стоп» — один `Army.stop` для одиночной и сетевой игры: снимает приказ,
  цель и режим боя, ставит `holdFire` до нового приказа.

### События и журнал

- `mapgen2/js/events.js` — правила: одно `attack` на владельца раз в 8 с
  (повторы в счётчик), `growth-stop` раз в 30 с, отказы без задержки.
- Событие адресуется владельцу. Хост/одиночная игра берут его из движка;
  клиент выводит свои `attack`/`destroy` из дельт снимка. В снимок события
  не кладутся.
- HUD: журнал последних событий (не всплывашка — в сети всплывашек нет),
  метка угрозы на мини-карте 10 с, действие «к месту атаки».

### Телефон и линия построек

- Указатели считаются по `pointerId`: один палец — камера/выбор/призрак, два —
  зум вокруг середины и панорама; отпускание после pinch ничего не ставит.
  `pointercancel` и смена ориентации жест гасят и правку НЕ подтверждают.
- На телефоне касание карты двигает призрак, подтверждение — кнопкой
  «Поставить»; для линии — два тычка и «Построить N».
- DPR ограничен (2 на coarse, 1.5 в экономии), миникарта не больше 2×,
  на телефоне по умолчанию 30 к/с (`Play.setFpsCap`, мир не замедляется),
  цели касания ≥44 px, safe-area через `env()`.
- Линия: шаг по повёрнутому пятну + 1 клетка, ≤20 зданий, предпросмотр всей
  серии (`renderer.lineGhost`), атомарная покупка.

## Финальная стабилизация 2026-10-26: что уже решено и нельзя откатывать

Правила ниже появились после разбора жалоб на встречный бой, исчезающий дом у
гостя, зависшие приказы, случайный редактор и общую остановку мира. Подробности
и числа — `research/patch-2026-10-26-final/{CONTRACTS,REPORT}.md`.

### Бой: угроза, самозащита и погоня — три разных числа

- **Марш не отсекает стычку конечной точкой.** `baseAnchor` при `v.order`
  возвращает клетку САМОГО воина с радиусом `AGGRO`; `v.order` — только куда
  идти. Раньше якорем была конечная точка, и у встречных армий с разными
  концами одна видела врага, а другая шла мимо без ответного урона.
- **Ответ на удар** разрешён в пределах `CONFIG.selfDefense` (3 клетки) и не
  фильтруется ни приказом, ни лагерем. Удар ставит `thinkT = 0`: реакция не
  зависит от id и фазы think.
- **Погоня** — от МЕСТА СТЫЧКИ: `_fightAnchor={x:v.x,y:v.y,r:FIGHT_LEASH}`;
  охрана лагеря/двора осталась с `CAMP_LEASH`. Не увеличивать поводок до
  острова.
- **Удары одного кадра применяются пакетом.** Сначала все пары, потом урон;
  добивающий удар погибшего в этом кадре считается. Порядок массива и
  владельца не должен давать систематическое преимущество.
- «Стоп»/`holdFire`: новых целей нет, ответ на близкий удар — есть.
- Приёмка: `node mapgen2/tools/combat-meet.js` — точный сценарий ТЗ, 5x5/20x20,
  дальние назначения, обратный массив, смена id/владельца, зеркало, лагерь,
  марш после боя, бой при `deferred`-бюджете, время реакции, пакетный удар.

### Путь: `deferred` — не «пути нет»

- `world._pathStop`: `'' | 'deferred' | 'limit' | 'unreachable' | 'invalid'`.
  `deferred`/`limit` НЕ снимают приказ, работу, обучение и груз, не пишут кеш
  недостижимости и не увеличивают счётчик неудач. На жителе —
  `routeStatus/routeDeferred`.
- Очередь справедливости: `beginFrame` выдаёт до двух гарантированных поисков
  самым долго ждущим; неиспользованное право возвращается. Счётчики
  `Metrics.pathDeferred/pathFairServed`, на жителе `pathWaitMax`.
- Ученик, не нашедший дорогу за `TRAIN_WAIT_MAX=20 с`, освобождает слот с
  событием `training-failed`, а не запирает его молча.
- Приёмка: `node mapgen2/tools/path-defer.js` — точный сценарий, виды отказа,
  дерево/груз/обучение, очередь 100/200 (p95/max по владельцам и позициям),
  точка атаки.

### Сеть: очередь сжатия видна ограничителю

- Backpressure всей цепочки: лимит и метрика — socket + gzip + pending, а не
  только `res.writableLength`.
- На поток — один ожидающий снимок, новый заменяет старый ДО сжатия. Байты
  gzip не выбрасываются; контрольные события и результаты команд — отдельная
  очередь. `close/error/abort` освобождают zlib/сокет/таймеры.
- `/api/build`, `/api/diag` (только хост), `/api/stream-stats` (только хост);
  в старте — `build/protocol/protocolWarning`, в снимке — `queue/queueWire/
  queueAge/serverNow`.
- `net.js`: deadline до конца чтения тела (не до заголовков), `finally` снимает
  busy, `generation` отсекает ответы старой партии, повтор команды — с тем же
  `n`, `unknown` не reject.
- TTL команды — по СЕРВЕРНОМУ `ageMs`, не по `Date.now` хоста минус `at`.
- Хост отдаёт `ids` и `appliedSeq`; сервер их сохраняет. Отметка «выполнено» —
  после бизнес-действия; исключение даёт `unknown` и остановку мира.
- Приёмки: `node game/tools/stream.js`, `node game/tools/http.js`,
  `node game/tools/mp.js`; `ping` меньше миллисекунды — это 1 мс сети, а не
  `wall` (иначе loopback-круг честно показывался как «главный поток»).

### Гость: действие видно сразу (`game/js/pending.js`)

- Ожидающая постройка рисуется тем же путём, что настоящая, но в мир НЕ
  входит: ни симуляция, ни работники, ни проходимость. В проверку НОВОГО места
  входит отдельным списком (`placeList`).
- `commandId` создаётся до отправки; согласование — по `ids` из результата, а
  пока результата нет — по версии снимка и точному владельцу/типу/повороту/
  пятну среди ПОЯВИВШИХСЯ построек. Старый снимок ожидание не стирает.
- Казна: `available = logs − Pending.reserved`; резерв освобождается ровно раз.
  Отказ/просрочка снимают ожидание, таймаут — `unknown` без повтора.
- `appliedSeq` + два снимка запаса завершают ожидание, если постройку снесли.
- Найм/обучение/приказ идут через `Play.clientCommand` и `Pending.addMark`;
  повтор по тому же жителю и лишние места блокируются с объяснением.
- Приёмки: `node game/tools/pending.js` (семантика) и `node game/tools/mp.js`
  (живой гость, хост с задержкой 450 мс: ноль пустых кадров, ноль двойной
  траты).

### Ввод: правка только удержанием и кнопкой

- `dblclick` правку НЕ открывает и пишется в след как проигнорированный.
- Удержание — один `pointerId`, одна постройка, непрерывное нажатие, 500 мс.
  Гасят: отпускание, `pointercancel`, `lostpointercapture`, `blur/hidden`,
  второй палец, панорама. Пока жест взят, `pointermove/up` слушаются на окне:
  отпускание над HUD больше не оставляет таймер живым.
- Запоздавший `pointermove` (главный поток был занят) распознаётся по
  `timeStamp` события: если сдвиг случился до порога — правка отменяется, дом
  не едет.
- Кнопка «Править» в табличке — намеренный второй вход.

### Ошибка подсистемы: мир останавливается явно

- Следующий `requestAnimationFrame` ставится ДО работы кадра; `keys`, `advance`,
  `draw`, `hud`, фоновый таймер и `catchUp` — за `guardFrame`.
- `Session.stepVillagers` ловит ошибку по одному жителю (id/место/состояние/
  работа), затем поднимает её; молча не продолжает.
- `Play.noteFault` пишет ограниченный стек/фазу/сущность, останавливает мир,
  показывает экран ошибки. Отказ промиса — не fatal, но пишется.
- Восстановление — из последней ЦЕЛОЙ контрольной точки (2 с) через
  `Serialize.hydrate`: груз, обучение и приказы сохраняются; до 2 с мира
  теряется, это честно написано на экране.
- «Выгрузить диагностику» — build/сервер, Metrics, след, команды, ожидания,
  бой, ожидания пути, checkpoint; токенов нет. След боя по умолчанию выключен:
  `Play.traceCombat([ids])`.

### Диагностика инцидента

Сервер: `/api/build`, `/api/diag`, `/api/stream-stats` (кольца ≤200, без
токенов). Хост/клиент: `Play.exportDiagnostics()` синхронно собирает то же без
сети; `Play.downloadDiagnostics()` добавляет серверную часть у хоста. Этого
достаточно, чтобы ответить «что было до потери хоста», а не только «хост
потерян».
