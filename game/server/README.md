# Сервер 4tox: лобби + серверная комната

Без npm-зависимостей: статика, лобби 2–4 и **авторитетная комната** в
`worker_threads.Worker`. Мир считает сервер, а не вкладка создателя: создатель
— обычный клиент. Транспорт прежний: SSE вниз, HTTP POST вверх; WebSocket и
брокеры не добавлялись.

Архитектура, форматы, checkpoint и пределы — [docs/MP_IMPLEMENTATION.md](../../docs/MP_IMPLEMENTATION.md).
Проверки и сырые результаты — [docs/MP_VALIDATION.md](../../docs/MP_VALIDATION.md).

```bash
node game/server/server.js            # 0.0.0.0:8787 + проверка сети
node game/server/server.js --tunnel   # плюс HTTPS-ссылка через pinggy
node game/server/server.js --local    # только 127.0.0.1, для одного
node game/server/server.js --open     # плюс открыть браузер
node game/server/server.js --port 9000
```

Двойной клик по `game/Мультиплеер.command` запускает `--tunnel --open`.

## Главное: почему «мой IP не отвечает»

У домашнего интернета бывает **CGNAT**: провайдер не даёт компьютеру
публичный адрес, а сажает его за общий NAT. Признак — роутер получает адрес
из `100.64.0.0/10` (или приватный), а сайты видят совсем другой IP. В этом
случае **входящие соединения до компьютера не доходят вообще**: ни ссылка по
IP, ни проброс порта в роутере не помогут — пакет умирает на стороне
провайдера.

Сервер проверяет это сам при запуске (через UPnP у роутера) и пишет в окно
прямо:

```
СЕТЬ: Archer C64, внешний адрес 100.118.36.208
ВНИМАНИЕ: провайдер держит вас за CGNAT (...)
Публичный IP 213.239.158.37 — общий; входящие до вас не доходят.
Проброс порта НЕ поможет: по внешнему IP друзья не зайдут.
```

Если CGNAT нет, сервер пробует **сам пробросить порт** через UPnP и пишет
ссылку по внешнему IP. Если UPnP выключен — порт надо пробросить вручную
(`TCP 8787` на IP этой машины); отключается флагом `--no-upnp`.

### Что работает при CGNAT

1. **Hamachi (это и есть «мой IP»).** В окне сервера и в лобби есть адрес
   вида `http://25.33.95.200:8787/game/`. Друг ставит LogMeIn Hamachi, входит
   в вашу сеть — и открывает этот адрес. Трафик идёт через Hamachi, CGNAT ему
   не мешает. В лобби это отдельная строка со своей кнопкой «копировать»;
   при запуске без `--tunnel` она главная, с `--tunnel` главная — HTTPS-ссылка.
2. **HTTPS-ссылка через туннель (`--tunnel`).** Другу ничего ставить не надо:
   он открывает `https://….pinggy.net/game/?lobby=XXXXX`, **один раз** жмёт
   «Enter site» на странице-предупреждении pinggy (это защита бесплатного
   туннеля) и играет. Первая загрузка идёт через релей: атласы игры весят
   ~9 МБ, поэтому это может занять до минуты. Дальше браузер их кэширует.
   Бесплатный туннель живёт час, потом адрес меняется — лобби покажет новый.
3. **Публичный IP.** Только если провайдер даёт входящие соединения (не
   CGNAT) и порт проброшен. Самый быстрый вариант, но зависит от провайдера;
   иногда достаточно позвонить и попросить «белый IP».

## Почему не cloudflared

Туннель cloudflared буферизует `text/event-stream`: события «кто вошёл», «кто
готов», «старт» и снапшоты не доезжают до браузеров. Именно из-за этого
раньше было «оба нажали Готов, а игра не началась». Pinggy — обычный
SSH-туннель, он стримит SSE как есть, поэтому годится.

Даже без туннеля SSE может порваться (ноутбук уснул, Wi-Fi моргнул). Поэтому
у лобби есть второй канал: пока экран лобби открыт, клиент опрашивает
`GET /api/status` раз в 1.5 с. Опрос возвращает то же состояние, что SSE, и
уже случившийся старт — старт не теряется. Сам старт начинает хост кнопкой
«Начать игру»: автостарт «как только все готовы» оставлял за бортом друга,
который ещё открывал ссылку.

## Как устроено

- `POST /api/lobby` — создать; `POST /api/join` — войти по коду;
  `POST /api/ready` — готовность; `POST /api/start` — старт (только хост),
  он же ждёт `ready` worker'а с первым committed baseline;
  `GET /api/status` — состояние лобби и комнаты; `GET /api/events?code&token`
  — SSE вниз, baseline при каждом новом подключении;
  `GET /api/server` — адреса сервера, CGNAT и туннель;
  `GET /api/ping` — круг и серверные часы (`c0/s1/s2`, tick, epoch);
  `GET /api/resume` — вернуть ту же партию после F5 (baseline + instance);
  `POST /api/command` — команда в серверную очередь (protocol 4);
  `GET /api/command-state` — точный `received/applied/rejected/...`;
  `POST /api/recover` — восстановление остановленной комнаты организатором;
  `POST /api/snapshot` — **409 `server_authoritative`**: мир от браузера больше
  не принимается.
- Мир считает `game/server/room-worker.js` (один worker на активную комнату),
  `room-runtime.js` ведёт очередь и commit, `persistence.js` — журнал и
  checkpoint. Главный поток не исполняет физику. `MAX_ACTIVE_ROOMS` (env, по
  умолчанию 1) даёт явный `server_capacity` вместо неограниченных worker'ов.
- 20 тиков/с по 50 мс; снимок после каждого второго committed тика (10/с).
  Часы — монотонные; `/api/ping` несёт `serverReceiveAtMs/serverSendAtMs`,
  клиент считает offset и `renderTime` по серверной шкале.
- Лобби стартует по кнопке хоста, когда все нажали «Готов». Игроков 2–4;
  старт одинаковый — ратуша, дом, лагерь лесоруба, три жителя.
- Игрок, у которого пропала связь, остаётся в лобби 45 секунд. В партии его
  отсутствие не останавливает комнату: мир идёт, пока есть хотя бы один
  игрок; после 10 минут без всех — `suspended_empty` с checkpoint.
- **Уход создателя в партии** больше не замораживает мир: он — обычный
  клиент. Клиенты получают снимки от комнаты; SSE можно переподключить,
  baseline придёт заново. Роль организатора для `/api/recover` передаётся
  детерминированно старейшему подключённому.
- **F5 не выкидывает в меню.** Клиент хранит код/токен, `roomId`, `epoch`,
  instance и sequence под ключом вкладки; `/api/resume` поднимает комнату из
  checkpoint+журнала при необходимости и отдаёт baseline. Нового игрока через
  `/api/join` после старта взять нельзя — это возврат.
- `STATE_DIR` (env; по умолчанию `./game/server/var/rooms`) — журнал,
  checkpoint и `lobby.json` комнаты. Файлы вне web-root, права 0700/0600, в
  git не идут.
- Наружу отдаются только `game/` и `mapgen2/`: корень репозитория (`.git`,
  документы, инструменты) по сети не ходит.

## VPS за reverse proxy (Caddy)

Сервер можно держать не на домашней машине, а на VPS. Node слушает только
loopback, наружу его отдаёт Caddy:

```bash
node game/server/server.js --host 127.0.0.1 --port 8787 --no-upnp \
  --public-url https://game.example.com/game/
```

- `--host` — не открывать порт Node в интернет. Раньше это умел только
  `--local`, но он ещё и отключал проверку сети, и лобби показывало ложное
  «порт наружу не проброшен».
- `--public-url` — единственная ссылка, которую лобби показывает друзьям.
  Без него `serverView` считает, что порт наружу не проброшен, и рисует
  предупреждение, хотя HTTPS уже работает.
- Caddy: `handle /game/*`, `/mapgen2/*`, `/api/*` → `reverse_proxy
  127.0.0.1:8787 { flush_interval -1 }`. `flush_interval -1` обязателен для
  SSE: иначе события лобби и снапшоты копятся в буфере.
- Статика отдаётся с `ETag`: повторный вход не скачивает 10 МБ атласов
  заново, браузер получает 304.
- Служба systemd: `WorkingDirectory=/opt/4tox`, `User=4tox`,
  `ExecStart=/opt/node/bin/node game/server/server.js ...`,
  `Restart=on-failure`.

Прежние замеры VPS 2 vCPU / 4 ГБ (Node ~60 МБ RSS, Caddy ~110 МБ, четверо
играют) относились к relay-схеме и к комнате на worker'е не переносятся.
Новый серверный прогон на VPS в этой сессии **не выполнялся**; локальный
CPU-бенч 100/200 сущностей — в [docs/MP_VALIDATION.md](../../docs/MP_VALIDATION.md).

**Прод и выкладка.** Боевой VPS — `374412.fornex.cloud` (он же naive VPN):
`4tox.service`, `/opt/4tox` без git, сборка для `/api/build` — файл
`/opt/4tox/COMMIT` (или env `BUILD_ID`). Порядок выкладки, проверки и отката —
[docs/DEPLOY.md](../../docs/DEPLOY.md). Caddy при выкладке игры не
перезапускается: он обслуживает и VPN.

## Производительность сети (правила, которые нельзя откатывать)

- **Снимок нумерован** (`revision`/`seq`). Клиент применяет только более
  новый; старый/повторный не мутирует даже HUD.
- **Убранное — битовая карта** hex-строкой; размер не растёт с числом
  срубленного.
- **Worker → main: один снимок in-flight.** Пока нет `snapshotAck`, worker
  держит только последний committed, а не очередь DTO.
- **Per-client: один pending snapshot.** Новый заменяет старый, gzip/сокет
  считаются вместе; очередь >2 МиБ или возраст >5 с закрывает этого клиента
  (`slow_client`), мир и других не останавливает.
- **Сжатие SSE** (gzip level 1 + `Z_SYNC_FLUSH`) обязательно: иначе поток
  снимков снова заполняет узкий канал. `Vary: Accept-Encoding`; новые
  подключения всегда получают полный baseline.
- **Команда не ждёт снимка.** `POST /api/command` → durable `accept` → fsync
  → 202 `received`; исполнение на границе тика. HTTP 200 не равен `applied`.
- **Команды идут по одной** с `commandId`/`clientSequence`; повтор того же ID
  возвращает прежний результат, другой payload — `command_id_conflict`.
  Хост-посредник в исполнении не участвует.
- **Сверка по id, не пересоздание.** `Serialize.apply` переиспользует
  постройки/жителей; `setBuildings` зовётся только при структурном изменении
  (F13). Обзор пересобирается при смене состава/места/рубки.
- **Одиночная/генератор** не подключаются к серверу и не зависят от него.

## Неактивные партии (правило заказчика, 2026-10-29)

Партия, в которой нет ни одного подключённого игрока, живёт **30 секунд** и
удаляется целиком: лобби, worker комнаты и её каталог в `STATE_DIR`.

- **«Подключён»** — живой SSE (`lobby.streams`) или запрос игрока (`lastSeen`)
  внутри окна. Скрытая вкладка держит SSE, поэтому фон идущую партию не
  убивает, а F5 успевает вернуться.
- `INACTIVE_TTL` (по умолчанию `30000` мс) — окно; `INACTIVE_SWEEP` — период
  проверки (не больше секунды). Оба читаются из env для приёмки.
- **Уход последнего игрока** через `/api/leave` закрывает партию сразу, не
  дожидаясь окна: `closeLobby` → `stopRoom` (штатный `shutdown` worker'у,
  `terminate` через 3 с, если не вышел) → удаление каталога. Это освобождает
  `MAX_ACTIVE_ROOMS`: иначе новая партия получает `server_capacity` («на
  сервере уже идёт другая партия»), а после рестарта Node старая комната ещё и
  поднимается из checkpoint.
- Проверка: `node game/tools/tests/mp-inactive.js` — лобби без SSE исчезает,
  живой SSE держит партию дольше окна, после закрытия она удаляется, уход
  последнего игрока освобождает слот и следующая партия стартует.

## Проверка

```bash
node --test game/tools/tests/*.test.js      # 66 unit/integration, без браузера
node game/tools/tests/mp-acceptance.js      # 15/15: HTTP/SSE, команда, resume
node game/tools/tests/mp-inactive.js        # неактивная партия удаляется за TTL
node game/tools/mp.js                       # 15 проверок на двух страницах Chrome
node game/tools/menu.js                     # одиночная игра в браузере
```

`mp-acceptance.js` поднимает изолированный сервер на loopback с временным
STATE_DIR и проверяет baseline, независимые тики, команду гостя, точный
результат, повтор ID, `409 server_authoritative`, уход создателя и F5-resume.
`mp.js` проходит тот же путь на real Chrome: две страницы, старт, снимки,
позы, команда, закрытие вкладки создателя. Оба скрипта не требуют боевого
VPS. `node game/tools/mp.js` — вход для прежней приёмки; подробности и
ограничения — [docs/MP_VALIDATION.md](../../docs/MP_VALIDATION.md).

Туннель проверяется вручную: `--tunnel`, открыть ссылку, один раз нажать
«Enter site», создать лобби и войти вторым браузером. Он зависит от внешней
сети, поэтому в `mp.js` не входит.
