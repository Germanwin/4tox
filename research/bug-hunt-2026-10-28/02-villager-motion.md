### BUG-02-01 · Переезд/поворот казармы оставляет весь двор на старом месте · major

- **Файл:** `mapgen2/js/villager.js:3259-3330` (`garrisonUpdate`), `:3230-3257`
  (`routeToBarracksYard`); связанные: `mapgen2/js/buildings.js:1715-1740`
  (`setSpot`/`touch`), `mapgen2/js/session.js:1424-1428` (`garrisonAt`).
- **Что происходит.** У военного лагеря есть «ключ места» (`v.campKey`), и при
  переезде лагеря воин пересчитывает путь к новому месту (`villager.js:3693-3698`).
  У двора казармы такого ключа нет вообще. Воин в состоянии `garrison` стоит на
  точке, которую когда-то выбрал `routeToBarracksYard`; после переезда казармы
  проверка «застрял» не срабатывает (клетка свободна), а `garrisonUpdate`
  выходит по `if (v.state === 'garrison')` — и больше ничего не делает. Воин
  остаётся на старом месте навсегда, `v.station` при этом указывает на
  переехавшую казарму, поэтому `Session.garrisonAt` продолжает считать двор
  занятым. Итог: дружина стоит в чистом поле и не возвращается на пост, а
  казарма отказывает в тренировке «двор полон», хотя новый двор пуст.
- **Почему баг (ожидалось / фактически).** Ожидалось то же правило, что у лагеря
  и лесорубского лагеря: место постройки изменилось — путь и место службы
  пересчитываются. Фактически двор и его вместимость привязаны к прошлому
  положению постройки: `garrisonAt` считает по ссылке `v.station === b`, а не по
  координатам, а `garrisonUpdate` не читает ни `b.x/b.y/b.rot`, ни `v.seen`
  (проверка `v.seen` там есть, но действует только при живом `v.path`).
- **Репро (node, настоящий движок).**
  1. `Session.startHome` на сиде `garrison-test`, добавить казарму через
     `Buildings.neighbourSpot` + `settle`, обучить 3 воинов, дождаться
     `state === 'garrison'`.
  2. `Buildings.setSpot(world, bar, {x: bar.x + 9, y: bar.y + 9})` — то же, что
     игрок делает мышью («ведение» + «Применить»).
  3. Прожить 40 с игрового времени шагами 1/60 через `Session.stepVillagers`.
  4. Вывод прогона:
     ```
     воины до: [{"x":41.5,"y":49.5},{"x":41.5,"y":47.5},{"x":41.5,"y":50.5}]
     казарма была {x:38,y:47} -> стала {x:47,y:56}
     воины через 40 с: [{"x":41.5,"y":49.5,"st":"garrison","spot":true}, ...]
     расстояние воин->центр НОВОЙ казармы: 11.0 | garrisonAt: 3 | capacity: 10
     ```
     Ни один не сдвинулся, `garrisonAt` = 3 (двор занят фантомами).
  5. Тот же эффект после «Стоп» на приказе: `Army.stop` снимает приказ, воин
     возвращается в `garrison` на месте приказа, потому что `v.garrisonSpot`
     не сброшен и ветка маршрута (`if (!v.garrisonSpot)`) не выполняется.
- **Доказательство.**
  ```js
  // villager.js:3301
  if (v.state === 'garrison') {
    idleStep(v, set, dt);          // единственный выход: стоим на старом месте
    return;
  }
  ...
  // villager.js:3314 — маршрут выбирается ТОЛЬКО если места нет
  if (!v.garrisonSpot) {
    if (!routeToBarracksYard(v, world, solid, b)) {
  ```
  Приёмка это не ловит: `mapgen2/tools/garrison.js` вообще не двигает казарму —
  в ней только тренировка, заполнение двора, `rebalanceGarrison` и «лагерь
  появился» (строки 101–140).
- **Уверенность:** высокая (воспроизведено, 40 с).
- **Правка (1–3 строки).** В начале `garrisonUpdate` — ключ места и сброс:
  ```js
  var sk = b.x + ':' + b.y + ':' + b.rot;
  if (v.stationKey !== sk) { v.stationKey = sk; v.path = null;
    v.garrisonSpot = null; v.state = 'toBarracksYard'; }
  ```

### BUG-02-02 · Погибший лесоруб навсегда оставляет дерево «занятым» · minor

- **Файл:** `mapgen2/js/combat.js:638-659` (`killVillager`); связанные:
  `mapgen2/js/villager.js:970-981` (`treesNear`/`keep`), `:1572-1579`
  (`unmark`), `:2547` (`fell` снимает метку).
- **Что происходит.** Метка цели живёт на дереве (`tree.mark = житель`). Снимают
  её три места: смена цели в `plan` (`mark` → `unmark` старого), падение дерева
  (`fell`) и увольнение (`Session.fire`). Смерть в этом списке отсутствует:
  `killVillager` обнуляет `employer`, `station`, `warcamp`, `path`, но не
  `v.tree`. `treesNear` отбрасывает любое дерево, у которого `tree.mark` стоит и
  не равен спрашивающему, — значит дерево, помеченное убитым, не выберет уже
  никто и никогда.
- **Почему баг (ожидалось / фактически).** Метка — это «кто на дерево целится»,
  а мёртвый не целится никуда. Фактически каждая смерть лесоруба (в бою, от
  набега) безвозвратно выводит из экономики одно дерево; накопленный эффект не
  лечится ничем.
- **Репро (node).** Нанять трёх в лагерь на сиде `mark-test`, дождаться
  `v.tree` (state `toTree` или `chop`), вызвать `Combat.killVillager(victim,
  world)`, затем `Villagers.treesNear(world, other.x, other.y, 24, other)`.
  Вывод прогона:
  ```
  дерево: 42.56,51.68 | state: toTree
  после смерти: tree.mark === victim (мёртвый)? true | mark.dead: true
  дерево попало в список целей другого рабочего? false | всего рядом: 24
  ```
  Дерево физически стоит, но в 24 ближайших его нет.
- **Доказательство.**
  ```js
  // combat.js:638 — ни unmark, ни v.tree = null
  function killVillager(v, world) {
    if (!v || v.dead) return;
    v.dead = true; v.hp = 0; v.hidden = true;
    ...
    v.employer = null; v.job = null;
    v.station = null; v.garrisonSpot = null; v.warcamp = null;
    v.anim = 'idle';
  }
  // villager.js:979 — метка любого чужого (в том числе мёртвого) скрывает дерево
  if (awayFrom && tree.mark && tree.mark !== awayFrom) return;
  ```
  Приёмка не ловит: `lumberjack.js` проверяет «у дерева под топором стоит метка
  этого рабочего», но никого не убивает; `combat.js` убивает воинов, а не
  лесорубов.
- **Уверенность:** высокая (воспроизведено).
- **Правка (1–2 строки).** В `killVillager` до `v.dead = true`:
  `if (v.tree && global.Villagers) global.Villagers.unmark(v, v.tree);`
  и затем `v.tree = null; v.goal = null;`.

### BUG-02-03 · Удар воина не проигрывается, и в сети у него фаза от прошлой анимации · minor

- **Файл:** `mapgen2/js/villager.js:3372-3384` (бой, `state='attack'`),
  `:3482-3489` (`armyMove`, `hold`), `:3301-3312` (`garrison`); связанные:
  `:2437-2451` (`setAnim` — единственное место, где зовётся
  `Replication.noteAnim`), `mapgen2/js/simulation/replication.js:48-73`,
  `game/js/snapshot-buffer.js:138-151`.
- **Что происходит.** В бою и в гарнизоне анимация ставится прямым присваиванием
  `v.anim = 'idle'; v.animWant = 'idle'`, а не `setAnim`. Из-за этого: (1) на
  хосте фаза кадра не двигается (`combatMove` сразу делает `return`, `idleStep`
  не зовётся) — воин стоит замороженным кадром `idle`, пока враг теряет HP;
  (2) в protocol 4 `noteAnim` не вызывается, поэтому клиент получает имя
  `idle`, но `animStartTimeMs/animDurationMs/animInstance` остаются от ПРОШЛОЙ
  анимации (обычно `walk`) — клиент играет `idle` с длительностью походки;
  (3) атлас `armored_villager` имеет `work` («удар мечом», `mapgen2/README.md`),
  но в бою он не берётся ни разу — удара не видно ни на хосте, ни у гостя.
- **Почему баг (ожидалось / фактически).** `AGENTS.md` описывает замах 0.35 с и
  бой как событие, которое видно; `setAnim` — единственный контракт с
  репликацией («клиент считает фазу от серверного времени и не перезапускает её
  на каждом снимке»). Прямое присваивание обходит и отрисовку кадра, и
  репликацию.
- **Репро.** Локально: обучить воина, дать приказ на врага, дождаться
  `v.state === 'attack'` — `v.anim === 'idle'`, `v.phase` не меняется между
  кадрами (сравнить два кадра подряд), спрайт стоит. В сети: `game/js/play.js`
  → `Replication.build` не кладёт `animInstance` для этого перехода.
- **Доказательство.**
  ```js
  // villager.js:3372-3383
  if (d <= C.ATTACK_RANGE && onMine) {
    v.path = null; ...
    v.state = 'attack';
    v.anim = 'idle';          // ни setAnim, ни noteAnim, ни сброса phase
    v.animWant = 'idle';
    ...
    v.rot = deg(Math.atan2(cy - v.y, cx - v.x));
    return;                   // фазу дальше никто не двигает
  }
  ```
  Приёмки не ловят: `game.js`/`menu.js` проверяют `knightSet` (что взят атлас
  воина), а не кадр удара; `combat.js` считает HP и время, картинку не смотрит.
- **Уверенность:** высокая по коду и по отсутствию вызова `noteAnim`; средняя по
  «насколько это видно» (зависит от того, смотрят ли на бой в этот момент).
- **Правка (1–3 строки).** В ветке `attack`: `setAnim(v, 'work', set);` и
  двигать фазу (как `idleStep`), либо хотя бы `setAnim(v, 'idle', set)` вместо
  прямых присваиваний; в `armyMove`/`garrisonUpdate` — то же.

### BUG-02-04 · Новая петлевая анимация у гостя первые ~150 мс показывается с конца цикла · minor

- **Файл:** `game/js/snapshot-buffer.js:138-151` (`animOf`), связанные:
  `game/js/play.js:945-972` (`presentNet`, `renderTime`), `game/js/server-clock.js:79-110`.
- **Что происходит.** `presentNet` рисует мир на `renderTime = simTime − 150 мс`
  (задержка интерполяции). `animOf` считает фазу от `animStartTimeMs`; для
  анимации, начавшейся только что, `e = (renderTime − start)/dur < 0`. Для
  не-петли фаза честно прижимается к 0, а для ПЕТЛИ берётся `e − floor(e)`, то
  есть при `e = −0.2` получается 0.8. Клиент ~150 мс (≈9 кадров при 60 к/с)
  показывает конец цикла новой анимации и только потом прыгает в начало.
- **Почему баг (ожидалось / фактически).** Ожидалось: новая петля начинается с
  первого кадра (как в ветке `loop === false`). Фактически каждый переход
  `idle↔walk↔work` у любого жителя на клиенте даёт рывок ног/топора.
- **Репро.** Посчитать формулу на числах из кода (ширина цикла `walk` = 8 кадров
  / 12 к/с = 0.6667 с, задержка 150 мс):
  ```
  отставание 20мс  walk: phase 0.97
  отставание 50мс  walk: phase 0.93
  отставание 100мс walk: phase 0.85
  отставание 148мс walk: phase 0.78
  ```
  В живом клиенте достаточно посмотреть на жителя в момент старта походки у
  гостя: первый кадр — из конца цикла.
- **Доказательство.**
  ```js
  // snapshot-buffer.js:145-149
  if (isFinite(start) && isFinite(dur) && dur > 0) {
    var e = (renderTime - start) / dur;
    if (loop) phase = e - Math.floor(e);          // e<0 -> фаза около 1
    else phase = Math.max(0, Math.min(1, e));     // а тут честный 0
  }
  ```
  Приёмка не ловит: `mp.js` проверяет формат и доставку снимков, а не номер
  кадра; визуального сравнения кадров у гостя нет.
- **Уверенность:** высокая по математике; средняя по заметности.
- **Правка (1 строка).** `if (!(e > 0)) phase = 0; else if (loop) ... else ...`.

### BUG-02-05 · Замах не работает, если цель замечена издалека: первый удар — в кадр входа в радиус · minor

- **Файл:** `mapgen2/js/combat.js:808-843`; связанные: `mapgen2/js/villager.js:3336-3473`
  (`combatMove`), `:3363-3384` (вход в радиус).
- **Что происходит.** `attackT = WINDUP` ставится в момент, когда цель ВЗЯТА
  (`t !== v.attackTarget`), и каждый тик убывает (`combat.js:766`). Если цель
  взята за 5 клеток, воин идёт к ней 3 с, `attackT` успевает стать 0, и в кадр,
  когда `d <= ATTACK_RANGE`, урон приходит сразу. Комментарий и `AGENTS.md`
  обещают обратное: «урон не приходит в тот же кадр, что цель вошла в дальность».
- **Репро (node, суша, 64×64, `windup-land`).** Два воина на расстоянии 5
  клеток; шаг 1/60, `Combat.tick` + `Session.stepVillagers`. Вывод:
  ```
  chase был: true | удар: 3.033 с | дистанция в удар: 1.20 | attackT в удар: 0.800
  ```
  `0.800` — это уже интервал `ATTACK_EVERY`, то есть замах не был применён;
  удар нанесён ровно в кадр входа в `ATTACK_RANGE` (1.2).
- **Доказательство.**
  ```js
  // combat.js:812-819 — замах выдаётся на ВЗЯТИЕ цели, а не на вход в радиус
  if (t !== v.attackTarget) {
    v.attackTarget = t;
    v.attackT = Math.max(v.attackT || 0, WINDUP);
    ...
  }
  // combat.js:840 — к приходу attackT уже 0
  if (v.attackT <= 0) { v.attackT = isBuilding(t) ? BUILDING_EVERY : ATTACK_EVERY;
    pending.push({ v: v, t: t }); }
  ```
  Приёмка не ловит: `mapgen2/tools/combat.js` (раздел «Замах») ставит воинов
  сразу в одной клетке от цели, поэтому `attackT` не успевает истечь.
- **Уверенность:** высокая (воспроизведено числом).
- **Правка (1–2 строки).** При переходе `combatMode` `chase → attack` (или в
  кадр первого `d <= ATTACK_RANGE`) ставить `v.attackT = WINDUP`, если удар по
  этой цели ещё не наносился.

### BUG-02-06 · `fell()` не проверяет, что дерево ещё в мире: лишние ходки в учёте · minor (латентный)

- **Файл:** `mapgen2/js/villager.js:2519-2523` (`strike`), `:2530-2566` (`fell`),
  `:4086-4092` (цикл ударов в `chop`).
- **Что происходит.** В одном кадре `chop` может прийтись несколько ударов
  (`hitBefore..hitAfter`), и `strike` зовётся в цикле. Первый удар на 5.000 с
  валит дерево (`fell`: `v.tree = null`, `v.state = 'carry'`), но цикл
  продолжается, `strike` снова видит `v.chopT >= CHOP_TIME` и снова зовёт
  `fell` — уже с `tree === null`. `fell` не проверяет `had` перед счётчиками:
  деревня получает +1 `felled` и +1 `inTransit` за дерево, которого нет. Ходка
  навсегда остаётся «в пути» — инвариант `logs + 4·inTransit = 4·felled` внешне
  сходится, но обещанных брёвен не будет никогда.
- **Репро (node).** Взять рабочего в `chop`, выставить `v.hits = 7;
  v.chopT = 4.99` и сделать ОДИН шаг с `dt = 1.3` (как это сделал бы внешний
  инструмент/приёмка с крупным шагом):
  ```
  felled + 3 | inTransit + 3 | дерево ещё в мире: false | state: carry
  инвариант: 12 vs 12
  ```
  На одно дерево — три ходки в учёте.
- **Почему это «латентный».** В игре шаг жёстко 0.05 с (`Play.advance`,
  `simulation.js: TICK_SECONDS = 0.05`, `mapgen2/app.js` — `Math.min(0.05, …)`),
  а `CHOP_HIT_EVERY = 0.625`; при таком шаге двух ударов в кадре не бывает.
  Дефект сработает при любом будущем увеличении шага (или в тесте с крупным
  `dt`), и тогда испортит казну навсегда — поэтому помечен.
- **Доказательство.**
  ```js
  // villager.js:2519
  function strike(v, world) {
    v.hits++;
    if (v.tree) v.tree.shake = 1;
    if (v.chopT + CHOP_EPS >= CHOP_TIME) fell(v, world);   // второй раз — tree=null
  }
  // villager.js:2530-2536 — had вычислен, но счётчики ниже не под ним
  var had = tree && keep.length !== objs.length;
  ...
  if (vill && v.employer) { vill.felled++; vill.inTransit++; }   // :2555
  ```
  Приёмки не ловят: `lumberjack.js` шагает 1/60 и проверяет ровно один удар на
  0.625 с.
- **Уверенность:** высокая по коду и воспроизведению; низкая по достижимости в
  текущем билде (dt ≤ 0.05).
- **Правка (1 строка).** В начале `fell`: `if (!tree) return;` (или `if (!had)
  { v.tree = null; return; }`).

### BUG-02-07 · Растворённого в казарме ученика можно выбрать мышью у стены · minor

- **Файл:** `game/js/play.js:2813-2823` (`villagerAt`), `:3035-3054` (`selectAt`);
  связанные: `mapgen2/js/villager.js:2972-2995` (`startTraining`,
  позиция = `entrance.in`), `:2350-2363` (`visibility`),
  `mapgen2/js/buildings.js:2061-2101` (`entrance`).
- **Что происходит.** `villagerAt` перебирает ВСЕХ жителей списка и не
  спрашивает `Villagers.visible`/`v.hidden`. Невидимого ученика закрывает от
  клика только приоритет постройки: `selectAt` сначала смотрит
  `renderer.buildingAt(cell)`. Но точка входа казармы лежит ВСЕГО в 0.27 клетки
  внутрь пятна (`entrance.in` при `mul = 0.7667`, `inY = 1.60`, пятно 3×4), а
  радиус выбора жителя — 0.34 клетки. Клик в свободной клетке сразу за стеной,
  в полосе ~0.07 × 0.4 клетки у двери, не попадает в постройку, но попадает в
  невидимого ученика.
- **Почему баг (ожидалось / фактически).** Правило: растворённый в казарме не
  рисуется и не выбирается (его нет на карте). Фактически выбор происходит, и
  HUD показывает «тренируется · N с» для человека, которого не видно; `H`
  уводит камеру к нему, а режим слежения (`state.follow`) ведёт камеру за
  невидимым.
- **Репро.** Обучить жителя, дождаться `v.hidden === true` (он в `entrance.in`),
  кликнуть на 1–2 экранных пикселя ЗА стеной казармы рядом с дверью при
  зуме ≈40: `villagerAt` вернёт скрытого ученика, `buildingAt` для этой клетки
  пуст.
- **Доказательство.**
  ```js
  // play.js:2817-2821 — ни hidden, ни visibility
  for (var i = 0; i < state.villagers.length; i++) {
    var v = state.villagers[i];
    var d = Math.hypot(v.x - p.x, v.y - p.y);
    if (d <= bestD) { bestD = d; best = v; }
  }
  ```
  Приёмки не ловят: `menu.js` проверяет, что растворённый не рисуется
  (`visibility`), но не пробует попасть в него мышью у стены.
- **Уверенность:** высокая по коду; средняя по «попадёшь ли» (полоса тонкая,
  ~3 × 17 px при зуме 42).
- **Правка (1 строка).** В цикле: `if (global.Villagers && !global.Villagers.visible(v)) continue;`.

### BUG-02-08 · Журнал событий: повтор атаки может обновлять выброшенное событие · minor

- **Файл:** `mapgen2/js/events.js:48-59` (`push`), `:64-90` (`throttled`).
- **Что происходит.** `throttled` держит агрегат `_evAgg[key] = { ev }` и при
  повторе правит поля самого объекта события. `push` при переполнении делает
  `arr.splice(0, arr.length - MAX)` — объект уходит из журнала, но остаётся в
  агрегате. Пока атаки идут чаще `ATTACK_GAP = 8` с, `throttled` только
  увеличивает `count` у выброшенного объекта и НЕ создаёт нового события —
  значит в журнале и в метке угрозы на обзоре («к месту атаки», `hud.js:433`,
  `:2469`) атака перестаёт обновляться до первой 8-секундной тишины.
- **Почему баг (ожидалось / фактически).** Повтор не должен теряться («повтор не
  теряется: у последнего события растёт count»); фактически он теряется, как
  только журнал насытился (40 событий — это несколько отказов стройки и
  сообщений о лесе).
- **Репро.** Заполнить журнал 40 событиями (`Events.refuse`), затем позвать
  `Events.attack` (создаст 41-е и вытеснит первое), ещё раз `Events.attack`
  через 1 с — новых событий в `Events.recent` не появится; проверить, что
  `_evAgg['attack:0'].ev` не входит в `world.events` (`indexOf === -1`).
- **Доказательство.**
  ```js
  // events.js:57 — выброшенное событие продолжает жить в агрегате
  arr.push(ev);
  if (arr.length > MAX) arr.splice(0, arr.length - MAX);
  // events.js:71-73 — повтор правит именно его
  if (last && last.ev && now - last.t < (gap || ATTACK_GAP)) {
    last.t = now;
    last.ev.count = (last.ev.count || 1) + 1;
  ```
  Приёмки не ловят: журнал проверяется на «событие появилось», а не на «оно
  осталось в массиве при переполнении».
- **Уверенность:** высокая по логике.
- **Правка (1–2 строки).** В `throttled` перед правкой проверять
  `arr.indexOf(last.ev) >= 0`, иначе создавать новое событие.

## Проверено и НЕ баг

- **Прямые пути не режут углы и не проходят сквозь занятые клетки.**
  Фаззер на 96×96 (`findPath` + `smoothPath`, 758 маршрутов, 3358 отрезков,
  плотная выборка 60 проб на клетку): **0 нарушений**. Правило «угол не
  срезаем» продублировано и в A* (`villager.js:810-811`), и в `lineClear`
  (`:891-893`), как и написано в `PATHFINDING.md`.
- **Версия карты занятых клеток надёжна.** `mapVersion` = длины объектов +
  длины построек + `_buildRev`; переезд/поворот дома меняет `_buildRev`
  (`buildings.js:1730-1738`), снос и рубка — длины. Совпадения версии у разных
  карт не бывает (счётчик только растёт).
- **Застревание в закрытой клетке не «лечится» телепортом в обычном ходе.**
  Гражданский/лесоруб: `stepOut` шагом (`villager.js:1100-1187`), перенос —
  только `rescueMove` как аварийный выход и только если шага нет; ученик и
  воин имеют такие же ветки. Это соответствует правилу заказчика «выходит
  шагом».
- **Кольцо военного лагеря.** Путь внутри строится по `campSolid(...,
  confine=true)` — открыты только `patrolCells`, модель 2×2 закрыта
  (`villager.js:2890-2946`); выйти «случайно» нельзя, есть только `stepOut` из
  модели. Это ровно то, что обещает `mapgen2/README.md`.
- **Вода, камни, деревья как препятствия.** `solidObject`: дерево и камень
  (кроме гальки) — да, куст/трава/цветы — нет; `blockedMap` и `walkable` —
  единственный источник для ходьбы и для боя (`attackLineClear` использует тот
  же кэш). Расхождения между «путь есть» и «идти можно» не нашёл.
- **«Скольжение» шага.** `SPEED_BOOST = 1.1` — сознательное отступление
  (10 % проскальзывания ступни), записано в шапке `villager.js:109-132` и
  проверяется `gait_probe`. Это правило, а не баг.
- **Выбор кадра поворота.** `Hero.nearestRot` при равном расстоянии берёт
  больший угол; для 8 поворотов это совпадает с `Math.round(deg/45)` всюду,
  кроме точной границы 337.5° (там 315° вместо 0°) — расхождение в один кадр на
  одной границе из 16, на поведение не влияет.
- **`v.hidden` в бою, отрисовке, обзоре и полосах HP.** `aliveVillager`
  исключает `hidden` и `trainee` (`combat.js:371-373`); `Renderer`,
  `Session.drawVillagers`, полосы HP и `hud.js` спрашивают
  `visibility`/`visible`. Единственная дыра — выбор мышью (BUG-02-07).
- **Смерть посреди пути.** `update` выходит по `v.dead`; оболочка/сервер
  вынимают мёртвых после шага, `freeCombatCell` вызывается, `noteDeadCargo`
  списывает груз в `lost` (`session.js:1329-1338`). Висячих ссылок на мёртвого
  в движении не нашёл (метка дерева — исключение, BUG-02-02).

## Не проверено

- **Живой браузер.** По условию не запускал `menu.js`, `mp.js`,
  `mapgen2/tools/game.js`; всё визуальное (BUG-02-03/04/07) подтверждено кодом
  и расчётом, но не скриншотом.
- **F5 хоста и `normalizeResumedVillagers`/`hydrate` в живом клиенте.**
  Прочитал: hydrate собирает жителя через `blank` (speed/rng/anchor на месте),
  путь/цель/дерево сбрасываются — по коду потери движения нет. Не проверял
  восстановление из checkpoint серверной комнаты (другой кодек,
  `simulation/checkpoint.js`), только глазами.
- **Ключ job'а `Navigation` не содержит карту проходимости**
  (`navigation.js:359`): один и тот же житель+назначение+клетки, но разные
  `solid` (например, `campSolid` и обычная карта) могли бы получить готовый
  путь от другой карты. Сценария, где это реально совпадает, не нашёл; помечаю
  как риск, а не находку.
- **`Villagers.areas(world, solid)`** кэшируется по версии мира и не учитывает
  переданную карту (`villager.js:579-614`). В игре её зовут только с обычной
  картой (`Army.areaAround`, `Combat.sameArea`), поэтому расхождения не
  воспроизвёл.
- **Удар сквозь модель своего лагеря** (`clearShot` пропускает пятно лагеря
  целиком, `combat.js:226-229`): при `ATTACK_RANGE = 1.2` и модели 2×2
  геометрически недостижимо, но проверял только расчётом.
- **Старый (protocol < 4) путь клиента**, `netSmoothVillagers` + `Serialize.apply`
  (`play.js:1509-1523`): в protocol 4 не используется, в браузере не гонял.
