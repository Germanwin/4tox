# Раскладка проекта 4tox

Этот файл — источник истины о том, что где лежит. Если папка переехала, а
здесь не поправлено, — неправ файл, и его надо привести в соответствие.

Написан 2026-10-14, когда проект был разложен по местам: до этого в корне
лежали вперемешку игра, девять ассет-проектов, три опыта скилла и два разбора,
и по папке нельзя было понять, боевое это или брошенное.

---

## 1. Принцип

**Один артефакт — одно место.** У каждой вещи есть ровно одна папка, где она
живёт, и ровно один способ до неё добраться. Как только у файла появляется
вторая копия «на всякий случай», порядок кончается: непонятно, какая копия
настоящая, и правка уходит не туда.

Второй принцип — **назначение важнее родства**. Опыт сборки кузницы и опыт
сборки амбара лежат рядом не потому, что оба про постройки, а потому что оба
одноразовые. Разбор чужого персонажа лежит не с персонажами, а с разборами.

## 2. Верхний уровень

```
4tox/
├── .gitignore      правила игнора — ТОЛЬКО здесь
├── AGENTS.md       правила работы агента
├── README.md       обзор проекта и карта репозитория
├── docs/           правила: этот файл и PIPELINE.md
├── mapgen2/        ИГРА
├── art/            МОДЕЛИ
├── research/       РАЗБОРЫ
└── experiments/    ОПЫТЫ
```

Четыре папки — четыре разных ответа на вопрос «что это». Новое кладётся в ту,
что отвечает на вопрос.

| Если это… | То это… | Куда |
|---|---|---|
| код, который видит игрок: карта, рендер, поведение | игра | `mapgen2/` |
| модель, которая поедет в игру спрайтом | производство | `art/<группа>/<имя>/` |
| замер, разбор, эталон, изучение чужого ассета | разбор | `research/<имя>/` |
| проба скилла, сравнение подходов, одноразовая сборка | опыт | `experiments/<имя>/` |
| правило, конвенция, разбор потока | документ | `docs/` |

**В корень не кладётся ничего.** Ни новой папки, ни нового файла. Появилась
потребность — сначала решается, какой это из четырёх ответов, потом создаётся
папка внутри.

## 3. Игра — `mapgen2/`

```
mapgen2/
├── index.html          точка входа, подключает атласы и модули
├── css/style.css
├── js/                 модули игры (IIFE поверх globalThis)
│   ├── rng.js          детерминированный ГПСЧ
│   ├── noise.js        шум
│   ├── worldgen.js     генерация острова: биом, деревья, камни
│   ├── sprites.js      разбор атласа и кадров
│   ├── buildings.js    постройки: посадка в пятно, зазор, масштаб
│   ├── waves.js        гребни волн
│   ├── hero.js         лесоруб
│   ├── villager.js     житель, маршрут, рубка
│   ├── render.js       отрисовка по глубине
│   └── app.js          сборка, панель, ввод
├── assets/             ТО, ЧТО ГРУЗИТ ИГРА (см. §5)
├── tools/              инструменты разработки и приёмки
│   └── out/            кадры приёмок, в git не идут
├── README.md           как устроена игра
└── PATHFINDING.md      как делать «дойти до ближайшего X»
```

Имя `mapgen2` оставлено намеренно. На путь `mapgen2/assets/sprites/atlas.json`
завязан поиск игры в трёх профильных скиллах
(`4tox-lowpoly-3d/scripts/canon.py::find_root`), и переименование ломало бы их
молча. Если когда-нибудь понадобится переименовать — сначала правится
`find_root`, потом папка.

### Инструменты игры

Приёмки в браузере (нужен Chrome) — `node mapgen2/tools/<имя>.js`:

| Скрипт | Что проверяет |
|---|---|
| `smoke.js` | генератор без браузера: доля суши, связность, объекты не в воде |
| `path.js` | поиск цели и маршрут без браузера |
| `place.js` | посадка ратуши: зазор, середина контура, поворот, клик |
| `townhall.js` | лист: 3 варианта × 4 поворота на настоящей карте |
| `villager.js` | житель в игре: атлас, ходьба, рубка, без шагов в воду |
| `house.js`, `hut.js` | прямоугольные постройки 3 × 2 на карте |
| `controls.js` | зум, панорама, подсветка клетки |
| `game.js` | начало партии: карта и ратуша игрока |
| `look.js`, `views.js` | кадры для глазами-проверки |

Кадры складываются в `tools/out/` — 57 МБ, в git не идут
(`mapgen2/tools/out/` в корневом `.gitignore`), перерисовываются прогоном.

Упаковщики атласов тоже здесь, хотя читают из `art/`: это инструмент **игры**,
он собирает то, что игра грузит. См. [PIPELINE.md](PIPELINE.md).

## 4. Производство моделей — `art/`

```
art/
├── README.md
├── buildings/      постройки: townhall, villager_house, lumbercamp
├── characters/     люди: villager
├── props/          предметы: axe, shovel
└── fx/             эффекты: waves
```

Группа выбирается по тому, **чем объект является в игре**, а не по тому, как он
сделан: лагерь лесоруба — постройка (ставится в пятно), топор — предмет
(носится в руке), волны — эффект (живёт на море).

### Каркас ассет-проекта

Обязательная форма. Если чего-то нет — так и должно быть, но лишнего быть не
должно:

```
art/<группа>/<имя>/
├── README.md            что это, числа, чем проверено, что не идеально
├── tools/               ГЛАВНОЕ: генераторы и упаковщики
│   ├── <имя>.py         геометрия на чистом Python, без bpy
│   ├── build_live.py    точка входа сборки в ЖИВОМ Blender
│   ├── build_<имя>.py   headless-рендер уже замороженной геометрии
│   ├── compose.py       пост-обработка: тень, контур, обрезка
│   ├── pack_*.py        упаковка в атлас игры (если проект её делает)
│   └── mcp.py/blmcp.py  клиент сокета blender-mcp (копия, можно править)
├── out/                 спрайты и выгрузки — то, что читает упаковщик
├── renders/            сырые рендеры Blender
├── <имя>.blend          сцена Blender
├── live_config.json     конфиг живой сборки (читает build_live.py)
└── live_<пресет>.json   именованные прогоны
```

`out/` и `renders/` — производные: их можно перерисовать из `tools/` и
`.blend`. Они лежат в git намеренно, чтобы был виден ход работы; если репозиторий
начнёт пухнуть, исключать надо начинать с них.

### Конфиги живой сборки

`live_config.json` — конфиг **по умолчанию**, его жёстко читает `build_live.py`
(`CONFIG = os.path.join(ROOT, 'live_config.json')`). Остальные —
именованные пресеты, их передают аргументом:

```bash
$PY tools/blmcp.py run tools/build_live.py --config live_4x.json
```

Поэтому они лежат **в корне проекта, а не в подпапке**: разносить конфиг по
умолчанию и пресеты по разным местам хуже, чем держать их вместе. Именование:
`live_config.json` — база, `live_<что>_<крупность>.json` — пресет
(`live_work_8_4x.json` — анимация работы, восемь поворотов, кадр 4×).

## 5. Что игра грузит и что лежит готовым

`mapgen2/assets/<имя>/` — это **результат**, а не исходник. Каждый такой
каталог — три файла одного атласа:

| Файл | Что внутри |
|---|---|
| `atlas.png` | сама картинка |
| `atlas.json` | метаданные: `ppu`, `az_deg`, `el_deg`, `res`, `mul`, `cell`, `anims`, `frames` |
| `atlas.js` | то же самое как `window.<ИМЯ>_ATLAS = {…}` — чтобы работало по `file://` |

Метаданные не украшение: по `ppu` и `az_deg`/`el_deg` рендер считает масштаб
спрайта, по `frames[].anchor` ставит точку опоры, по `footprint` и `mul` сажает
постройку в пятно с зазором, по `ground` — по середине наземного контура.

| Атлас | Подключён в игре | Кто собирает |
|---|---|---|
| `sprites/` | да, `index.html` | унаследован, исходных моделей нет |
| `townhall/` | да, `index.html` | `mapgen2/tools/pack_townhall.py` |
| `waves/` | да, `index.html` | `mapgen2/tools/pack_waves.py` |
| `hero/` | да, `index.html` | унаследован, исходных моделей нет |
| `villager/` | да, `index.html` | `art/characters/villager/tools/pack_atlas.py` |
| `textures/` | да, `app.js` (картинки, не атлас) | — |
| `house/` | **нет**, лежит готовым | `art/buildings/villager_house/tools/pack_atlas.py` |
| `hut/` | **нет**, лежит готовым | `mapgen2/tools/pack_hut_rect.py` |
| `lumbercamp/` | **нет**, лежит готовым | `art/buildings/lumbercamp/tools/pack_lumbercamp.py` |

Дом, хижина и лагерь собраны и упакованы заранее, но в `index.html` не
подключены: слой построек в игре пока знает один тип — ратушу. Подключение
описано в `art/buildings/townhall/HUT3x2.md`.

## 6. Правила

### 6.1. Глубина и вычисление корня

Ассет-проект лежит на `art/<группа>/<имя>` — **три уровня** от корня. Скрипт в
его `tools/` считает корень так:

```python
HERE = os.path.dirname(os.path.abspath(__file__))
ROOT = os.path.dirname(HERE)                                  # сам проект
REPO = os.path.abspath(os.path.join(ROOT, '..', '..', '..'))  # корень 4tox
```

Для скриптов ещё глубже (в `references/`) уровней больше — считается по месту.

Тех, кто эти пути считает, сейчас тридцать шесть. Если глубина изменится, чинить
надо всех:

* `art/buildings/*/tools/` — 6 файлов (`present.py`, `present_hut_rect.py`,
  `pack_atlas.py` у дома, `sheet.py` у дома и ратуши, `pack_lumbercamp.py`,
  `place_lumbercamp.py`);
* `art/characters/villager/tools/pack_atlas.py` — 1 (у него путь до корня
  длиннее: `tools → villager → characters → art`);
* `art/props/{axe,shovel}/tools/sheet_*.py` — 2;
* `references/` в `research/hero` и `art/characters/villager` — 24 (по 12);
* `mapgen2/tools/pack_{townhall,hut_rect,waves}.py` — 3, там
  `REPO = os.path.dirname(ROOT)`.

Проверка одной командой — она должна молчать:

```bash
grep -rn "/Users/" --include=*.py art mapgen2 research experiments
```

Считать это число вручную не надо:

```bash
grep -rl "REPO *=" --include=*.py . | grep -v __pycache__ | wc -l
```

### 6.2. Абсолютных путей внутрь репозитория нет

Ни в коде, ни в документации. Абсолютный путь ломается при первом же переезде
и ломается молча. Внешние пути (`~/.dsh/skills/...`) — можно: они не наши.

### 6.3. Правила игнора живут в одном месте

Только корневой `.gitignore`. Никаких `.gitignore` внутри проектов: правило,
разбросанное по папкам, находят не все.

Что не коммитится: `__pycache__/`, `*.pyc`, `.DS_Store`, `*.blend1` (Blender
кладёт рядом с `.blend` предыдущее сохранение), `*.bak`, `mapgen2/tools/out/`.

`*.blend1` и `*.bak` не коммитятся, поэтому **удалять их надо осознанно**: в
истории их нет. Ручную копию, которая ценна как версия, сначала коммитят
(`git add -f`), потом убирают с диска.

### 6.4. Игра не читает `art/` напрямую

Единственный мост — упаковщик и `mapgen2/assets/`. Игра не знает ни про
`out/`, ни про `renders/`, ни про `.blend`. Поэтому ассет-проект можно
переставить целиком, ничего в игре не трогая, — лишь бы упаковщик нашёл `out/`.

### 6.5. Именование

* Сцена Blender носит имя проекта (`villager`, `shovel`, `lumbercamp`).
* Объекты и материалы — свой префикс (`vg_`, `vh_`, `lc_`, `shovel_`), чтобы
  в живом Blender не столкнуться с чужими объектами и чистить только свои.
* Кадры атласа — `<префикс>_<анимация>_<кадр>_<поворот>`
  (`villager_work_5_270`), у построек `<префикс>_<вариант>_<поворот>`
  (`townhall_b_90`).
* Файлы спрайтов в `out/` — то же имя, что у кадра.

### 6.6. Числа — в README проекта, не в переписке

У каждой модели в README есть таблица: пятно, габарит, трис, ppu, чем проверено
и **что осталось неидеальным**. Последнее обязательно: без него следующий
человек примет известный дефект за новый.

## 7. Известные отступления

Честный список мест, где раскладка не идеальна. Это не «потом поправим», а
осознанный выбор; если менять — то с причиной.

1. **В `art/buildings/townhall/` живут два здания** — ратуша и хижина
   (`hut_rect`). У них общий пайплайн: `thpipe.py` (камера, свет), `geom.py`
   (проекция, тень), `compose.py` (контур). Разводить их по папкам — значит
   либо дублировать пайплайн, либо городить импорт через полрепозитория. Хижина
   описана в `HUT3x2.md`, упаковщик у неё свой — `mapgen2/tools/pack_hut_rect.py`.
   **Правило на будущее:** здание выносится в свою папку, когда у него
   появляется свой пайплайн, а не раньше.

2. **Две одинаковые папки `references/`** — `research/hero/references/` и
   `art/characters/villager/references/` совпадают побайтово. Житель делался по
   эталону героя, и его проект держит замеры у себя, чтобы не зависеть от
   соседа. Дублирование осознанное: проект должен читаться целиком.

3. **`live_*.json` лежат в корне проекта**, а не в подпапке, — см. §4.

4. **`assets/sprites/` и `assets/hero/` не воспроизводятся из этого
   репозитория.** Они унаследованы от прежних проектов (`mapgen/`, затем
   `atlas3d/`), которых на диске больше нет, — вместе с исходными моделями.
   Это единственные атласы, у которых нет пары в `art/`.

5. **`research/coc_house/` без README.** Этюд дома: `.blend`, `out/*.glb`,
   рендеры, папка `tools/` с генератором. Что именно проверялось — не
   записано.

6. **Клиент blender-mcp лежит в проектах под двумя именами** — `blmcp.py`
   (shovel, villager_house, villager, ab_plain) и `mcp.py` (lumbercamp,
   ab_skill, forge_demo). Это **один и тот же файл**, 150–152 строки,
   различаются только шапки. Расхождение пришло из скиллов:
   `4tox-building-forge/scripts/scaffold.py` создаёт в новом проекте
   `tools/mcp.py`, а `4tox-lowpoly-3d` учит `tools/blmcp.py`. Пока скиллы не
   договорились, переименование в репозитории починило бы половину и сделало бы
   проекты непохожими на то, что их породило. **Правило:** новый проект берёт
   имя из скилла, которым собирается; в этом репозитории канон — `blmcp.py`.
   Файл намеренно лежит в проекте копией, а не в общем месте: проект должен
   собираться, будучи скопированным наружу.

## 8. Чек-лист перед коммитом

1. Новое лежит в `art/`, `research/` или `experiments/` — не в корне?
2. Абсолютных путей не добавилось? (`grep -rn "/Users/" --include=*.py …`)
3. `__pycache__`, `*.blend1`, `.DS_Store` не в индексе? (`git status --short`)
4. Если модель поехала в игру — упаковщик прогнан **и атлас в `mapgen2/assets/`
   изменился**? Если не изменился, а должен был, — упаковщик смотрит не туда.
5. Числа и «что неидеально» записаны в README проекта?
6. Новая папка верхнего уровня не появилась?
